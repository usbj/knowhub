# 前台审核时间线展示 — 功能细节补充

> 日期：2026-07-04
> 状态：待前台开发时落地（当前前台尚未创建开发）
> 背景：博客审核流程已落地后台部分（流水表/状态机/回避/后台详情审核历史折叠区），前台展示作为「代替通知」的审核结果传达闭环，需在前台文章详情页落地。本文档维护前台落地的功能细节，供前台开发时直接参考。

## 一、定位

前台文章详情页展示**该文章的审核时间线**，让作者（及任何读者）被动看到文章从提交到发布的审核全过程，包括驳回意见——无需主动通知即可闭环传达审核结果。

与后台「审核历史」折叠区共用同一份数据源（`blog_review_log` 表）和同一个后端接口（`GET /blog/review-log/{blogId}`），区别仅在展示位置与样式：
- **后台**（已落地）：管理端详情弹窗内折叠区，审核员视角，含审核员账号便于审计
- **前台**（本文档）：读者侧文章详情页时间线，作者/读者视角，展示审核过程与意见

## 二、接口（已就绪，前台直接复用）

`GET /blog/review-log/{blogId}` → `Result<List<ReviewLogVo>>`

- **权限**：当前挂 `knowhub:blog:info`（后台详情权限）。**前台落地时需评估**：
  - 若前台文章详情本身是公开访问（无需登录），则审核时间线接口需另开**无鉴权**版本或 permitAll 放行（类似 `/file/public/**`）
  - 若前台文章详情需登录才可见，则复用现有鉴权接口即可
  - 建议方案：前台读者侧只需看「已发布文章」的审核时间线，可在前台用独立接口 `GET /blog/public/{blogId}/review-log`（无鉴权，仅返回 PUBLISHED 文章的流水），与后台鉴权接口分离，避免后台权限键暴露给前台
- **返回字段**：`reviewLogId/blogId/action/operator/operatorNickname/role/advice/createTime`
  - `action` 见字典 `blog_review_action`（SUBMIT/APPROVE/REJECT/REVOKE/PUBLISH）
  - `operatorNickname` 由后端 left join sys_user 带出，前台直接展示昵称不必二次查询
  - `operator`(username) 作为账号快照保留，前台一般不展示账号串

## 三、展示设计（建议）

### 3.1 位置
文章详情页正文之后、评论区/相关推荐之前，作为文章背景信息的一部分。可折叠，默认收起（避免干扰阅读），标题「审核记录」或「修订历史」。

### 3.2 内容
按 `createTime` 升序的时间线，每条展示：
- **动作标签**：DictTag 渲染 `blog_review_action`（提交审核/通过/驳回/撤回/直通发布），带字典配置的颜色
- **操作人**：`operatorNickname`（昵称，无昵称回落 operator 账号）
- **时间**：`createTime` 格式化
- **审核意见**：`advice` 非空时展示（驳回必填、通过可选），支持换行

### 3.3 角色展示策略（前台隐私考量）
- 前台是否展示「审核员是谁」需产品定：
  - **展示昵称**：透明度高，但审核员可能不希望被读者关联
  - **仅展示动作+意见，不展示操作人**：保护审核员隐私，仅作者在后台能看到具体审核员
  - 建议：前台时间线**不展示 operator/operatorNickname**，仅展示「动作 + 时间 + 意见」；审核员身份留在后台详情弹窗。后端接口字段不变，前台渲染时选择不展示 operator 字段即可
- `role` 字段（AUTHOR/REVIEWER/SYSTEM）前台可转化为语义化描述：作者提交/审核员通过/系统直通，比裸露的 role code 友好

### 3.4 主题适配
前台沿用 rookie-ui 的 `--rookie-*` 变量体系（深浅模式自动跟随），时间线样式参考后台 `BlogDetailDialog.vue` 的 `.blog-detail__timeline*` 类，前台可复用相同视觉语言。

## 四、数据可见性约束

- 审核时间线**仅对已发布(PUBLISHED)文章**展示在前台——草稿/待审/驳回/撤回的文章前台本就不可见，其流水也不应暴露
- 若文章当前是 PUBLISHED，但历史有 REJECT 记录（驳回→改→再提审→通过），这些驳回记录**是否展示**需产品定：
  - **展示全量**：体现审核严谨性，读者能看到文章曾被打回并改进
  - **仅展示 APPROVE/PUBLISH**：只给最终结果，隐藏过程波折
  - 建议：**展示全量**，审核过程透明更可信，驳回意见本身也是内容质量的一部分信号

## 五、落地步骤（前台开发时）

1. 评估前台文章详情页鉴权方式（公开/登录），决定审核时间线接口走公开版还是鉴权版
2. 若需公开版：后端新增 `GET /blog/public/{blogId}/review-log`（无鉴权，校验 blog 为 PUBLISHED 后返回流水），并在 `SecurityConfig` permitAll（需用户许可改 rookie-framework）
3. 前台文章详情页组件拉取流水，按 §3 设计渲染时间线
4. 字典 `blog_review_action` 前台需能加载——若前台复用 rookie-ui 的 dict store 自动预加载则无需额外处理；若前台是独立工程需确认字典加载机制
5. 主题适配深浅模式

## 六、与通知的关系

当前用「前台时间线 + 后台审核记录」展示代替通知。未来若 rookie 通知模块支持个人通知（投递给单个 userId），可在 `BlogServiceImpl.notifyReviewResult` 接入，主动推送给作者「您的文章《xx》已通过/被驳回」，与展示闭环并存（通知是主动触达，展示是被动查阅，互补）。详见 [blog-review-flow-design.md](./blog-review-flow-design.md) §七。
