# KnowHub 项目第三阶段开发任务规划

## 1. 本阶段定位

本文所说的“三阶段”是 KnowHub 项目的第三阶段开发，不是把本次工作再次拆成三个开发阶段。本阶段的主题是：以 Agent 能力建设为主线，同时补齐账号、安全、互动、UI、运营和 CI/CD 检索，使 KnowHub 从知识内容平台升级为可扩展的智能知识工作平台。

当前仓库中的主要边界如下：

- `knowhub`：文章、博客、资源、项目、评论、审核、历史记录、文件存储等 KnowHub 业务后端。
- `rookie-common`、`rookie-framework`、`rookie-system`、`rookie-admin`：用户、权限、系统配置、通知、日志、定时任务、文件和管理后台基础能力。
- `knowhub-ui`：KnowHub 业务端前端。
- `rookie-ui`：系统管理端前端。

本阶段新增的 Agent 能力不放进现有 Java 业务模块中强行实现，而是新增独立的 Python Agent 后端服务，服务名为 `knowhub-agent`。整体调用关系为：

```text
knowhub-ui / rookie-ui
          ↓
Java 业务后端（认证、用户、权限、已有业务资源、对外 API）
          ↓ 内部服务调用
Python knowhub-agent（Agent Runtime、Model Gateway、RAG 编排、Skill、自定义 Agent）
          ↓
模型供应商 / 向量与全文检索 / 外部 CI/CD 连接
```

Java 后端仍然是面向前端的业务入口和身份边界；Python 服务只提供内部 Agent 能力接口，不直接暴露给浏览器。Java 负责把当前用户身份、资源范围和必要的授权上下文传递给 Python，Python 只负责 Agent 相关的执行、检索和模型调用，不重复实现整套用户、角色和后台权限系统。

本仓库已经存在一部分可复用基础：Spring Security、Token 与 Redis 中的用户上下文、`@PreAuthorize` 权限、系统配置缓存、通知模块、文件存储、定时任务以及 Java 异步日志能力。本阶段只对这些能力做 Agent 场景的扩展和跨服务适配，不再另起一套通用登录、权限或异步基础设施。

本阶段不建议按“做完一个大功能再做下一个大功能”的方式推进，而应按下面的模块并行拆分任务。每个任务都标记了前置条件，前置条件未完成时不要直接把功能暴露给用户。

## 2. 本阶段总体目标

本阶段完成后，系统应具备以下能力：

1. 用户可以安全注册、登录、验证邮箱、通过邮箱找回密码，并管理自己的会话和隐私。
2. 系统可以统一接入多个模型供应商，动态选择系统 Key 或用户私人 Key，并进行调用限制、配额和审计管理；本阶段暂不建设计费能力。
3. 用户可以创建知识库，通过知枢 RAG-Agent 使用关键词检索、向量检索、重排和引用回答问题。
4. 用户可以使用面试 Agent 进行多轮面试训练，获得基于回答证据的评分和改进报告。
5. 用户可以创建和管理 Skill，并据此创建、测试、发布、分享和回滚自定义 Agent。
6. 管理员可以配置多条 AI 日报生成计划，决定每日生成数量、生成时间、日报主题、数据范围和通知范围；用户可以浏览日报历史。
7. 用户可以私信、接收通知、提交反馈，并在业务端获得统一、稳定的交互体验。
8. 系统可以把代码仓库、提交、PR、Pipeline、Job、日志和部署记录接入知识库，支持 CI/CD 流程化检索。
9. 所有 Agent、模型、知识库、密钥、日报、消息和 CI/CD 数据均有清晰的所有权、权限、审计和删除策略。

## 2.1 术语草案（待确认）

以下术语先作为本计划中的临时约定，不代表已经写入开发文档或 `README.dev`。在正式开发前由项目负责人确认；确认后再同步到 API 文档、数据库设计、开发文档和 `README.dev`。

- **Agent：** 面向用户或系统场景的可运行智能应用定义，包含提示词、模型策略、Skill、工具、知识库和权限。
- **Agent Runtime：** Python `knowhub-agent` 中负责加载 Agent 版本、组装上下文、调用模型、运行工具和生成 Run 事件的执行内核。
- **Agent Run：** 一次具体的 Agent 执行实例，包含用户、会话、Agent 版本、模型、检索、工具调用、用量、结果和失败状态。
- **Skill：** 可被 Agent 复用的能力单元，包含输入输出协议、提示词或实现、工具白名单、依赖、版本和权限。
- **Tool：** Agent 可以调用的受控外部能力，例如知识检索、读取 KnowHub 资源、查询 CI/CD 状态或等待人工确认。
- **Knowledge Base：** 用户或团队管理的知识集合，包含数据源、文档、分块、索引、ACL 和版本。
- **Credential Ref：** 对系统 Key、团队 Key 或用户私人 Key 的不可读引用；业务日志和 Agent Run 只保存引用，不保存密钥原文。
- **Model Gateway：** Python 服务内统一适配聊天、Embedding 和重排模型的调用层。
- **Retrieval Trace：** 一次检索的查询改写、召回、融合、重排、ACL 过滤和引用证据记录。

本计划中的术语可以继续调整，但在确认之前不应直接作为对外 API、表名或 README 的最终规范。

## 2.2 CI/CD 优先原则

本阶段的第一批工作不是先做某个 Agent 页面，而是先把整个项目的交付链打通。Java 后端、`knowhub-ui`、`rookie-ui` 和 Python `knowhub-agent` 都要有独立、可重复执行的检查和构建步骤；后续每一个 Agent 底座或业务功能都必须在这条流水线上验证。

第一批先完成 CI 基线：Java Maven 编译/测试、两个前端的类型检查/构建、Python 服务的依赖检查/单元测试、统一的环境变量与敏感配置注入、产物版本标识、基础安全扫描和分支门禁。此时 Python 服务可以先以最小健康检查服务接入流水线，不需要等待 Agent Runtime 完成。

随后建立开发、测试和预发布环境的 CD 骨架，至少能部署 Java、两个前端和 Python 服务，执行健康检查和冒烟测试。数据库迁移、向量索引、模型 Key、外部连接和回滚策略随着对应功能逐步接入；不能因为 Agent 尚未完成就推迟整个交付链。

## 2.3 Agent 底座先行原则

真正开始知枢 RAG-Agent、面试 Agent、Skill 挂载和自定义 Agent 之前，应先完成第 5、6 章的底座任务。第 5 章负责模型供应商、动态凭据和调用控制，第 6 章负责 Agent 定义、会话、双层记忆、工具、流式执行和 Run 审计；这些能力必须在 Python `knowhub-agent` 中形成可复用内核，不能由每个具体 Agent 各自实现一套。

底座完成的最低标准是：

- Python 服务可以独立启动，并通过 Java 内部协议接收经过验证的用户和资源授权上下文。
- Model Gateway 可以选择系统 Key、团队 Key 或用户私人 Key，但业务代码看不到 Key 原文。
- Agent 可以加载不可变版本，创建会话，召回当前 Agent 专属长期记忆，拼接短期上下文，并生成可追踪的 Run。
- 工具调用有注册、Schema、权限、超时、取消、步数和人工确认机制。
- 流式输出、异步 Run、失败恢复、记忆写入、记忆删除和 Run 审计已经可被多个 Agent 复用。

只有底座验收通过后，才进入第 7、8 章的知枢、面试、Skill 和自定义 Agent 产品实现。面试 Agent 的难度策略、题库素材和画像字段是产品层配置；长期记忆的召回、注入、隔离和存储流程属于底座能力。

## 2.4 实际执行顺序

本文的任务编号用于追踪任务，不完全代表开发先后。实际执行顺序调整为：

1. 先做 `P3-59` 的多服务 CI 基线，并建立 Python `knowhub-agent` 的最小项目骨架和健康检查。
2. 接着做 `P3-60` 的开发/测试环境部署骨架、服务发现、配置注入、健康检查和基础回滚；先支持空壳服务，后续持续扩展。
3. 完成 `P3-01` 至 `P3-05`，确定 Java-Python 边界、内部 HTTP 协议、身份上下文、数据所有权和任务状态。
4. 完成 `P3-06` 至 `P3-18`，复用并扩展 Java 现有身份、权限、Redis、配置、通知和异步能力，建立模型与凭据底座。
5. 完成 `P3-19` 至 `P3-25`，在 Python 服务中完成 Agent Runtime、短期记忆、Agent 专属长期记忆、工具、流式执行和 Run 审计。
6. 完成 `P3-26` 至 `P3-42`，依次实现知识库/RAG、AI 日报、面试 Agent、Skill 和自定义 Agent；每个功能都必须进入既有 CI/CD 流程。
7. 完成 `P3-43` 至 `P3-58`，补齐私信、通知、反馈、UI 和 CI/CD 数据检索能力。
8. 最后完成 `P3-61`、`P3-62`，做质量大盘、安全、压测、灾备、全链路验收和正式发布。

## 3. Agent 服务边界与已有基础复用

这里的任务不是重新做一遍总体架构，而是把新增 Python 服务和现有 Java 系统之间的职责写清楚。具体功能任务仍需在各自描述中注明“Java 负责什么、Python 负责什么、前端调用谁”。

### P3-01 建立独立 Python Agent 服务

**服务归属：** 新增 Python `knowhub-agent`；Java 负责服务注册、配置下发和对外业务接口。

**前置条件：** 已有 Java 模块、前后端入口、部署环境和当前接口清单。

**实施内容：** 建立独立的 Python 项目、依赖管理、配置管理、日志规范、健康检查、启动方式和容器化方式。Python 服务负责 Agent Runtime、Model Gateway、RAG 编排、Skill 执行和自定义 Agent 运行；Java 不直接嵌入 Python 解释器，也不把供应商 SDK 和 Agent 编排代码写进 Java。

**交付与验收：** `knowhub-agent` 可以独立启动、健康检查和部署；生产环境只允许 Java 通过内部网络访问；Agent 相关代码、依赖和运行日志不会混入现有 Java 构建链。

#### 结构中的职责约束

- `api` 和 `workers` 只负责接收请求、转换协议和触发用例，不直接编写完整 Agent 业务逻辑；
- `application` 负责组织一次具体用例，例如创建 Run、执行索引、生成日报或完成面试报告；
- `domain` 负责 Agent、记忆、检索、工具、Skill 和工作流的核心规则，不直接依赖 FastAPI、具体数据库或某个模型供应商 SDK；
- `infrastructure` 负责 Redis、队列、向量数据库、模型供应商、Java 内部 API 和密钥解析等外部实现；
- `workers` 负责长时间执行，不能让 Embedding、批量索引、日报生成或 CI/CD 同步长期占用 FastAPI 请求线程；
- `prompts` 只保存 Prompt 模板及其变量定义，Prompt 的版本和配置快照需要进入 Run 或业务结果记录；
- `contracts` 保存 Java-Python 双方共同理解的请求、事件、错误和状态模型，协议变更需要兼容窗口和契约测试。

建议的依赖方向为：

```text
api / workers → application → domain
                      ↓
              infrastructure adapters
```

实际项目可以将目录合并或拆分。例如小规模初期可以把 `application` 与 `domain` 的部分文件合并，也可以暂时不单独建立 `migrations` 或某些 Worker 目录；但不应因此让浏览器直接访问 Python、让 Python 直接修改 Java 业务表，或让 RAG-Agent、面试 Agent 各自复制一套 Model Gateway、记忆和权限实现。

#### Agent 类型与共用底座

知枢 RAG-Agent、面试 Agent 和自定义 Agent 建议实现统一的运行接口，例如 `AgentRunner` 或等价抽象，由不同 Agent 提供自己的 Prompt、MemoryPolicy、RetrievalPolicy、个性化参数和工具白名单。共用底座包括：

- Model Gateway、模型供应商适配和凭据引用；
- 短期上下文、长期记忆存储、抽取、合并、召回和注入；
- 工具注册、Schema、权限、超时、取消、步数和人工确认；
- 流式事件、异步 Run、失败恢复、用量统计和审计；
- Java 内部 API 调用、请求追踪和错误映射。

因此，该结构的目标是帮助复用底座，而不是要求每种 Agent 都必须对应固定的目录或类名。最终实现可以采用其他经过评估的 Python Web 框架、任务队列或 Agent 编排库，但必须说明替代方案对协议、流式输出、任务恢复、测试和运维的影响。

### P3-02 定义 Java 与 Python 的内部调用协议

**前置条件：** P3-01。

**实施内容：** 第一版沿用现有 Spring MVC + JSON `Result<T>` + HTTP Controller/Service 的方式定义 Java → Python 内部 REST 协议，不引入当前项目没有使用的 Feign、gRPC 或消息总线。协议至少包括用户身份摘要、请求追踪 ID、Agent/会话/Run ID、资源范围、语言和调用来源；定义 Python → Java 的流式事件、最终结果、错误、引用、用量和异步任务状态。协议需要明确超时、重试、幂等、版本兼容和服务不可用时的降级行为。

**交付与验收：** Java 前端接口不需要了解 Python 的内部实现；Python 服务不能信任浏览器传来的 userId 或权限字段；双方可以独立发布并在兼容窗口内完成协议升级。

### P3-03 复用现有身份与权限上下文

**服务归属：** Java 复用现有认证和权限链路；Python 增加 Agent 资源级授权校验和必要的 Java 回调。

**前置条件：** P3-01、P3-02；现有 `TokenVerifyFilter`、`UserInfo`、`@PreAuthorize` 和权限菜单链路可用。

**实施内容：** Java 复用现有 `TokenVerifyFilter`、Redis 中的 `UserInfo`、`SecurityContext` 和 `@PreAuthorize` 完成浏览器请求的登录用户识别、基础角色权限和资源归属判断，再通过内部 HTTP 调用传递短生命周期、可验证的授权上下文。浏览器的 `Token` 请求头不能直接作为 Python 服务的信任凭据；Java-Python 之间需要单独的服务身份校验和防重放机制。Python 只补充 Agent、知识库、Skill、Run 和检索结果的资源级权限；需要判断 KnowHub 文章、资源、项目、文件等既有业务权限时，通过 Java 内部接口或授权结果校验，不复制一套 SysUser/SysRole 权限系统。

**交付与验收：** 浏览器不能绕过 Java 直接调用 Python；Python 不能接受未经签名或过期的用户身份；用户无法通过修改 Agent、知识库、Run 或文档 ID 越权访问数据。

### P3-04 扩展现有异步、Redis 和通知能力

**服务归属：** Java 复用现有异步配置、Redis、通知和定时任务；Python 只实现 Agent 运行所需的异步执行和状态回传。

**前置条件：** P3-01、P3-02；现有 `AsyncConfig`、Redis 缓存、通知 Service/Controller 和已有定时任务可用。

**实施内容：** Java 侧继续复用现有 `@Async`、`AsyncConfig`、`MigrationAsyncConfig`、Redis、通知和定时任务能力，但只承载适合当前线程池/调度器的轻量任务、状态回调和通知。现有默认 `logExecutor` 使用 `DiscardOldestPolicy`，不能直接承载不能丢失的 Agent 记忆写入或长时间 Agent Run；Python 为长时间 Agent Run、Embedding、索引、报告和 CI/CD 同步提供自己的 worker/任务机制。两边通过 Run/Job ID、幂等键和状态回调衔接，不重复建设 Java 已有的通知和缓存能力。

**交付与验收：** 前端能看到统一的处理中、成功、失败和重试状态；重复回调不会重复写入；Python 服务重启后任务状态和 Run 记录仍可恢复；通知统一走现有通知体系。

### P3-05 划分 Agent 数据和既有业务数据的所有权并建立迁移策略

**服务归属：** Java 继续拥有用户、文章、博客、资源、项目、评论、文件和系统通知等既有业务数据；Python 拥有 Agent 执行、检索索引和 Agent 专属运行数据。

**前置条件：** P3-01、P3-02、P3-03。

**实施内容：** 明确哪些数据由 Java 数据库权威保存，哪些数据由 Python 服务保存，哪些数据通过 Java 业务 API 只读获取。Java 新增业务表继续沿用当前 MyBatis Mapper/XML、PageHelper、实体/VO/Quarry 和 `sql/*.sql` 初始化脚本的项目习惯；当前没有发现 Flyway 或 Liquibase，不在计划中强行引入。Python 服务数据库和向量索引使用 Python 服务自己的迁移/初始化机制。Python 不直接修改 Java 的用户、文章、资源和权限表；Java 不直接修改 Python 的向量索引和 Agent 运行内部状态。跨服务删除、归档和权限变更第一版通过内部 HTTP API、状态回调或幂等同步任务完成；不默认引入消息总线。

**交付与验收：** 形成数据归属清单、跨服务调用清单、删除/归档/权限变更同步规则；任何数据都有唯一权威来源，不依赖跨服务直接读写对方数据库。

### 已有基础复用清单（非新增任务）

本阶段的 Agent 开发默认复用以下已有能力，不再把它们当作从零建设的前置项目：

- **认证与基础权限：** `rookie-framework` 已有 `SecurityConfig`、`TokenVerifyFilter`、`UserInfo`、`@PreAuthorize` 和权限菜单链路。新增 Agent 权限只补 Agent/知识库/Skill/Run 的资源权限和 Java-Python 授权上下文，不重写用户角色体系。
- **Redis 与系统配置：** `rookie-common` 已有 `RedisCache`、`SysConfigUtil` 和系统配置缓存。模型目录、Agent 开关、配额和功能开关优先接入现有配置体系，但密钥原文不能放入普通系统配置值。
- **异步与定时：** `rookie-framework` 已有 `AsyncConfig` 和日志异步执行器，`knowhub` 已有审核、文件清理和报表等定时任务。它们可继续承载 Java 侧轻量异步和调度；Python 的长时间 Agent Run、Embedding、索引和 CI/CD 同步另设适合的 worker/队列，并通过任务 ID 与 Java 衔接。
- **通知：** `rookie-system` 已有通知、通知分组、已读和前端通知状态能力。私信、Agent 完成、密码重置和 CI/CD 告警应扩展现有通知事件，不再另建一套通知中心。
- **文件与业务内容：** `knowhub` 已有文件对象、存储后端、文章、博客、资源、项目和评论等业务能力。Python 通过 Java 内部 API 或受控数据同步读取，不直接连接 Java 业务表。
- **审计与日志：** 现有操作日志、错误日志和异步落库能力继续使用；Python 新增运行日志必须接入相同的追踪 ID、脱敏和审计关联规则。

## 4. 身份、账号与安全基础

**实施内容：** 梳理登录、刷新、注销、单设备退出、全设备退出、会话过期和异常登录处理。会话记录需要包含设备标识、登录时间、最近活跃时间、IP 摘要和撤销状态。

**交付与验收：** 用户可以查看和撤销自己的会话；密码修改或安全事件可以吊销指定会话或全部会话；Token 过期和撤销均有自动化测试。

**交付与验收：** 注册、验证、重发、过期和重复使用流程完整；未验证账号的权限边界明确；邮件模板、链接域名和环境配置可管理。

### P3-08 实现通过邮箱找回密码

**前置条件：** P3-04、P3-06、P3-07。

**实施内容：** 使用一次性、短时有效的重置 Token；重置页面不能回显旧密码；成功重置后使相关旧 Token 失效，并按策略吊销旧会话。

**交付与验收：** 无论邮箱是否存在都返回统一结果；Token 不能重复使用、不能猜测、不能在日志中出现；重置成功和失败都有审计事件。

### P3-09 完善密码策略和登录风险控制

**实施内容：** 统一密码强度、修改密码、登录失败限流、验证码/挑战、异常设备提醒、异地登录提醒和敏感操作二次确认。必要时为管理员和高风险操作增加 MFA 扩展点。

**交付与验收：** 暴力尝试被限速；正常用户有可恢复的解锁路径；风险事件不会把密码、Token 或私人 Key 写进日志。

**交付与验收：** 用户能控制个人资料和互动权限；注销流程可追踪、可重试、不会留下可继续使用的 Token；保留数据符合隐私和审计要求。

### P3-11 建立敏感数据、日志和审计安全基线

**前置条件：** P3-03、P3-06。

**实施内容：** 统一对密码、Token、Cookie、模型 Key、邮箱验证码、环境变量、CI/CD 密钥和用户隐私字段脱敏。审计记录保存“谁在什么时候以什么身份做了什么”，但不保存密钥原文和完整敏感请求。

**交付与验收：** 异常堆栈、接口日志、监控标签、前端上报、Prompt 记录和导出文件均经过脱敏扫描；管理员查看审计记录也无法恢复私人 Key。

## 5. 模型供应商、动态 Key 与调用控制底座

### P3-12 建立模型供应商和模型目录

**服务归属：** 目录管理和用户可见配置由 Java 管理；模型能力、供应商适配配置和运行时读取由 Python `knowhub-agent` 使用。

**前置条件：** P3-02、P3-03。

**实施内容：** 抽象供应商、模型、模型能力、上下文窗口、Embedding、重排、限流、区域、健康状态和默认策略。Java 管理端配置优先复用现有 `sys_config`、`SysConfigUtil` 和 `ConfigReader` 约定；密钥原文不进入普通系统配置。模型名称、调用限制和能力不应散落在 Agent 业务代码中。本阶段不设计模型价格、账单、支付、充值或费用结算。

**交付与验收：** 管理员可以启用、禁用和配置模型；Agent 只依赖统一模型标识；供应商变更不需要改动业务 Agent。

### P3-13 实现统一 Model Gateway

**服务归属：** 完全属于 Python `knowhub-agent`；Java 只负责接收前端请求、传递调用上下文和返回结果，不直接调用模型供应商 SDK。

**前置条件：** P3-12、P3-11。

**实施内容：** 为聊天模型、Embedding 模型和重排模型提供统一调用接口，兼容流式文本、非流式文本、结构化输出、工具调用和错误码转换。供应商 SDK 只能存在于适配层。

**交付与验收：** 至少支持两类模型调用协议或两个供应商；上层 Agent 不直接依赖厂商 SDK；调用失败可以归类为鉴权、限流、超时、内容拒答或服务异常。

### P3-14 实现 KMS/HSM 和应用密钥分离

**服务归属：** 密钥所有权和管理接口由 Java/密钥服务控制；Python 只能在受控模型调用期间取得短生命周期的运行时凭据，不拥有后台读取能力。

**前置条件：** P3-11、部署环境具备密钥管理能力。

**实施内容：** 使用 KMS、HSM 或独立密钥服务保存主加密密钥。数据库只保存密文、密钥版本、摘要和状态；应用运行身份只能获得必要的解密权限，管理员后台不具备读取接口。

**交付与验收：** 完成加密、解密、密钥轮换、旧版本兼容、撤销和灾备恢复演练；数据库备份和导出中没有可直接使用的模型 Key。

### P3-15 实现系统模型 Key 的安全管理

**服务归属：** Java 提供管理员操作和凭据元数据；Python Model Gateway 负责使用凭据调用模型。Java 和 Python 均不得提供返回明文 Key 的业务接口。

**前置条件：** P3-13、P3-14。

**实施内容：** 管理员可以新增、替换、禁用和测试系统 Key，但只能看到供应商、状态、更新时间和末四位。Key 只在 Model Gateway 受控调用时解密，不经过普通配置查询接口。

**交付与验收：** 前端、接口、日志、监控和审计都无法获取明文；替换后新调用立即使用新 Key；禁用后不能继续调用。

### P3-16 实现用户私人模型 Key 的强隐藏存储

**服务归属：** Java 负责用户归属、增删改、脱敏展示和权限；Python 通过内部凭据租约或受控密钥接口使用 Key，不保存 Key，不把 Key 返回给前端或普通管理接口。

**前置条件：** P3-14、P3-15、P3-04。

**实施内容：** 用户 Key 与用户资源绑定，使用信封加密或外部密钥服务保存。用户只能新增、替换、验证、撤销和查看脱敏摘要，不能再次查看原文；管理员不能通过后台、导出、SQL 直读或普通运维接口获得明文。当前 `SecurityConfig` 中存在 admin 对 `@PreAuthorize` 的直通逻辑，因此 Key 的 Controller 不能只依赖普通管理员权限注解，必须单独设计“可管理元数据但不可读取明文”的策略，并在服务层和密钥服务层双重阻断明文读取。

**交付与验收：** 用数据库、管理端、接口抓包、日志检索和备份恢复进行反向验证；所有路径均不能还原明文。文档必须明确“平台管理员不可读，但受控运行时可短暂使用”的技术边界。

### P3-17 实现凭据选择和动态注入策略

**服务归属：** Java 负责确定当前用户和允许使用的凭据范围；Python 负责在 Agent Run 内选择模型和凭据，并在调用完成后销毁运行时引用。

**前置条件：** P3-13、P3-15、P3-16。

**实施内容：** 按请求用户、Agent 所有者、供应商、模型能力、配额策略和用户选择，决定使用系统 Key、团队 Key 或用户私人 Key。向下游只传递短生命周期的运行时凭据引用。

**交付与验收：** Agent 不直接读取数据库密钥；运行记录只保存 `CredentialRef`；用户删除或撤销 Key 后，新的调用立即失效。

### P3-18 实现模型健康、降级、重试、熔断和用量控制

**服务归属：** Python 负责模型调用级健康、重试和熔断；Java 负责用户/系统侧调用限制、配额配置、管理端展示和审计查询。本任务不包含计费、账单或支付。

**前置条件：** P3-13、P3-17。

**实施内容：** 增加供应商健康检查、超时、指数退避、不可重试错误识别、模型降级、调用次数/Token 用量统计、用户调用限制、Agent 调用限制和异常用量告警。用量统计只用于运行监控、限流和故障排查，不转换为金额，也不形成账单。

**交付与验收：** 单一供应商故障不会拖垮全站；重试不会造成失控调用；能够按用户、Agent、模型和时间段查询调用次数与 Token 用量；系统不出现价格、账单、支付和扣费流程。

## 6. Agent Runtime、工具与会话平台

### P3-19 建立 AgentDefinition 和版本生命周期

**服务归属：** Agent 定义、版本和运行配置由 Python `knowhub-agent` 管理；Java 负责用户所有权、管理端入口、外部 API 和权限上下文。

**前置条件：** P3-02、P3-04、P3-12。

**实施内容：** 定义 Agent 名称、描述、角色提示词、模型策略、Skill、工具、知识库、权限、配额、状态和版本。支持草稿、测试、发布、下线和回滚。

**交付与验收：** 发布后的版本不可变；每次运行绑定具体版本；草稿修改不影响已经发布的 Agent 和历史运行回放。

### P3-20 实现 Agent Runtime 最小执行循环

**服务归属：** 完全属于 Python `knowhub-agent`；Java 不实现 Agent 循环，只负责调用、鉴权、流式转发和业务资源授权。

**前置条件：** P3-13、P3-19。

**实施内容：** 实现加载版本、组装系统上下文、读取会话、调用模型、处理结构化结果、返回答案和记录运行状态的基础循环。先支持无工具对话，再逐步接入检索和工具。

**交付与验收：** 可以运行一个最小 Agent；失败有明确错误和 Run 状态；上层产品不需要重复实现模型调用和上下文拼接。

### P3-21 实现会话、消息、上下文窗口和历史压缩

**服务归属：** Agent 会话和上下文由 Python 管理；Java 只保存或转发前端需要的业务索引、权限结果和审计关联，不直接拼装 Prompt。

**前置条件：** P3-20。

**实施内容：** 该任务只负责短期记忆：支持会话创建、消息分页、用户消息、Assistant 消息、工具调用消息、工具返回消息、当前检索结果、上下文截断、摘要压缩、重新生成、消息删除和会话归档。短期记忆是当前会话的工作上下文，不跨 Agent 共享；删除或撤回后的内容不能继续进入模型上下文。

**交付与验收：** 长会话不会无限增长到超过模型上下文窗口；短期上下文的保留、截断和压缩策略可配置；用户消息和工具消息顺序稳定；历史分页、删除、恢复和权限校验均有测试。

### P3-22 实现双层记忆、Agent 专属长期画像和 Run 审计

**服务归属：** 双层记忆、长期画像召回、画像更新和 Agent Run 由 Python `knowhub-agent` 管理；Java 负责用户身份、画像管理入口、删除/导出请求、通知和必要的业务审计，不读取其他 Agent 的长期记忆。

**前置条件：** P3-20、P3-21。

**实施内容：** 建立短期记忆和长期记忆两层结构，并明确长期记忆按“用户 + 具体 Agent”隔离。知枢 RAG-Agent、面试 Agent 以及每个用户自定义 Agent 都必须拥有独立的长期记忆空间，不能使用一个全局用户画像互相污染。

#### 短期记忆

短期记忆来自当前会话上下文，包括用户消息、Assistant 消息、工具调用与返回、当前检索证据、当前任务计划和必要的会话摘要。它服务于当前会话的连续对话和工具协作，遵循上下文窗口管理策略，不因为一次会话结束就自动变成长期记忆。

#### 长期记忆

长期记忆是某个用户在某一个具体 Agent 下持续积累的用户画像和稳定事实，例如面试 Agent 下的技术掌握情况、薄弱知识点、表达习惯、历史面试问题和练习建议；知枢 RAG-Agent 下则可以是用户常用的知识范围、偏好的回答方式、常用 Skill 和经用户确认的长期偏好。两者互相隔离，不能因为同一个 userId 就直接共享。

长期记忆记录至少包含 `userId`、`agentId`、记忆类型、内容、来源 Run/会话/学习记录、置信度、创建时间、最近验证时间、更新时间、状态和可见性。记忆应支持追加、去重、合并、降权、过期、用户确认、用户修改和用户删除，不能只保存一段不可解释的大文本。

#### 新会话的长期记忆召回与注入

每次新会话开始时，Python 服务先根据具体 `agentId`、用户输入、Agent 目标和权限范围召回相关长期记忆；召回结果经过去重、时效性、置信度和敏感信息过滤后，注入该 Agent 的系统提示词上下文。不能把其他 Agent 的画像、当前用户无权访问的内容或未经确认的高风险推断注入模型。

最终发给模型的上下文由两类记忆共同组成：一是当前会话的短期记忆，包括正常上下文和工具消息；二是当前 Agent 专属的长期记忆召回结果。除此之外，再按 Agent 需要拼接当前问题、知识库检索证据、Skill 指令和工具 Schema，并明确各部分的优先级和不可覆盖关系。

#### 长期记忆的写入与存储流程

一次 Run 结束或产生关键事件后，Python 从对话、工具结果、评分、学习记录和用户主动输入中提取候选记忆；经过规则校验、敏感信息过滤、重复判断、置信度评估和 Agent 隔离校验后写入长期记忆存储。需要较重处理的画像摘要、知识点掌握度和建议生成走 Python worker；写入、更新和删除都保留来源与版本，支持重新计算和审计。

#### 记忆存储建议

Python 服务应把数据库作为长期记忆的权威存储，把 Redis 或其他缓存只用于短期上下文、事件流和热点画像缓存。长期记忆至少需要区分“记忆事实/画像条目”“记忆来源与版本”“候选记忆”“当前画像摘要”“记忆状态/置信度”和“用户删除或纠正记录”。如果后续需要语义召回，可以为长期记忆建立独立索引，但索引只是召回加速层，不能替代权威记录，也不能跨 `agentId` 查询。

建议的生命周期是：

1. Run 或学习事件产生候选记忆。
2. Python worker 做敏感信息过滤、结构化抽取、去重、合并和置信度判断。
3. 通过 `userId + agentId` 命名空间写入长期记忆事实，并保留来源 Run/会话/学习记录和版本。
4. 更新该 Agent 的画像摘要、知识点掌握度或偏好索引，同时产生可追踪的记忆变更事件。
5. 新会话按 `agentId`、当前问题、记忆类型、时效性和置信度召回，并在注入系统提示词前再次做权限和敏感信息过滤。
6. 用户查看、确认、纠正、删除或清空记忆时，通过 Java 对外提供入口，由 Python 执行实际变更并回传结果；删除需要同步清理缓存和召回索引。

这一流程允许面试 Agent 和知枢 RAG-Agent 复用同一套记忆内核，但两者的长期记忆数据、画像规则、召回范围和提示词注入内容始终隔离。

#### Run 审计

同时保存用户、Agent 版本、模型、CredentialRef、开始/结束时间、Token、检索、工具调用、短期记忆摘要、长期记忆召回 ID、失败原因和最终状态。敏感内容按策略保存摘要或脱敏结果；Run 记录可以说明“使用了哪些记忆”，但不允许管理员通过审计接口读取用户私人 Key 或其他 Agent 的长期画像。

**交付与验收：** 新会话能够只召回当前 Agent 的相关长期记忆，并与短期上下文共同组成最终模型上下文；知枢、面试和自定义 Agent 的长期记忆相互隔离；一次学习或面试结果可以按来源写入画像；用户可以查看、纠正、删除或清空自己的 Agent 长期记忆；可以按 Run 追踪执行链和记忆召回链，管理员只能看必要的脱敏诊断信息。

### P3-23 实现流式输出、取消、超时和恢复

**服务归属：** Python 负责执行取消、超时和事件游标；Java 负责把 Python 的流式事件安全转发给前端，并处理登录态失效和业务侧限流。

**前置条件：** P3-20、P3-22。

**实施内容：** 第一版优先采用现有 Spring MVC 可承载的 SSE/流式 HTTP 方式，不默认引入 WebSocket starter；支持用户主动取消、服务器超时、浏览器断线恢复和后台任务转异步。取消必须传播到模型流和工具调用；如果后续私信场景确实需要双向实时通信，再单独评估 WebSocket。

**交付与验收：** 前端能够实时显示生成状态；取消后不会继续发起模型调用或长时间占用 worker；断线后可以从事件游标恢复。

### P3-24 建立工具注册表、Schema 和权限白名单

**服务归属：** 工具注册和执行器属于 Python；涉及已有文章、资源、项目、文件、用户和通知的工具必须通过 Java 内部 API 或授权回调访问，禁止 Python 直连 Java 业务表。

**前置条件：** P3-04、P3-20。

**实施内容：** 每个工具登记输入输出 Schema、资源权限、网络权限、超时、重试、调用次数/Token 限制和审计等级。数据库写入、私信发送、文件删除、部署和命令执行等危险工具默认关闭。

**交付与验收：** 未登记工具无法被模型调用；模型输出不能绕过工具授权；工具参数经过服务端 Schema 校验和资源级权限校验。

### P3-25 实现人工确认、步数限制和安全中断

**服务归属：** Python 负责运行时中断和确认状态；Java 负责把确认请求作为业务事件展示给用户，并在确认时重新校验用户权限。

**前置条件：** P3-24。

**实施内容：** 为发送消息、修改资源、发布、部署和其他有副作用的动作增加人工确认；增加最大步数、最大运行时间、最大 Token/调用次数、循环检测和安全中断。

**交付与验收：** Agent 只能提出危险动作，不能默认执行；出现循环、异常工具响应或调用次数/Token 超限时，Run 能安全停止并解释原因。

## 7. 知识库、混合检索与知枢 RAG-Agent

### P3-26 实现知识库和数据源管理

**服务归属：** 知识库的用户入口、KnowHub 文章/资源/项目引用和基础权限由 Java 管理；Python 管理 Agent 使用的知识库快照、数据源处理和索引状态。

**前置条件：** P3-04、P3-05、P3-19。

**实施内容：** 支持知识库创建、编辑、归档、删除、所有者、可见范围、协作者和数据源。数据源统一支持文件、URL、文本、KnowHub 文章、博客、资源、项目文档和后续 CI/CD 数据。

**交付与验收：** 用户可以管理知识库和数据源；删除有软删、异步索引清理和恢复策略；重复内容按内容哈希或版本去重。

### P3-27 实现解析、清洗、分块和元数据抽取

**服务归属：** 解析、分块和元数据抽取主要在 Python worker 中完成；Java 负责已有文件对象和业务内容的授权读取、上传入口及任务展示。

**前置条件：** P3-05、P3-26。

**实施内容：** 为 Markdown、PDF、DOCX、HTML、纯文本、代码和日志建立解析适配器；统一进行清洗、标题层级识别、分块、语言识别、来源位置和更新时间抽取。

**交付与验收：** 解析结果可预览；每个分块都有稳定 ID、来源文件、位置、版本、所有者和 ACL；解析失败进入可重试任务。

### P3-28 复用现有召回底座并评估向量/重排扩展

**服务归属：** 索引、Embedding 和重排由 Python `knowhub-agent` 管理；Java 只通过内部接口查询索引任务状态，不直接维护向量索引。

**前置条件：** P3-13、P3-27。

**实施内容：** 优先复用项目文档中已经落地的 ngram 全文检索和跨内容标签体系，不另起一套重复的全文检索引擎。在现有召回效果评测不足时，再增加 Embedding 向量召回和重排作为扩展通道；记录索引版本、Embedding 模型、分块策略和更新时间，并支持增量更新、批量重建和索引迁移。

**交付与验收：** 现有 ngram、标签召回可以被 Python `knowhub-agent` 调用；是否启用向量和重排由评测结果决定；模型或分块策略变化时可以重建新版本而不破坏旧版本。

### P3-29 实现混合召回、融合、去重和 ACL 过滤

**服务归属：** Python 执行混合检索和 Agent 侧 ACL 过滤；已有 KnowHub 资源的最终授权以 Java 提供的权限上下文或内部授权回调为准。

**前置条件：** P3-04、P3-28。

**实施内容：** 以 ngram 全文、跨内容标签为基础，按需要增加向量召回；支持多通道结果融合、权重、阈值、TopK、去重和重排。权限过滤必须尽可能在召回和进入上下文之前完成，而不是只在前端隐藏。

**交付与验收：** 有固定测试集验证关键词、语义、混合和权限过滤结果；无权文档的标题、片段、数量和相似度都不会泄露。

### P3-30 实现查询改写、追问理解和引用链

**服务归属：** 查询改写、检索编排和 Retrieval Trace 由 Python 保存；引用跳转到文章、资源、项目和文件时由 Java 提供对外详情和再次鉴权。

**前置条件：** P3-21、P3-29。

**实施内容：** 将多轮问题改写为独立检索查询，识别时间、范围、项目和实体过滤；回答必须保存检索查询、召回结果、重排结果、最终引用和过滤原因。

**交付与验收：** “它”“上面提到的方案”等追问可以正确继承必要上下文；每个重要结论都有来源或明确标注无法确认。

### P3-31 实现知枢 RAG-Agent

**服务归属：** 知枢 Agent 完全运行在 Python `knowhub-agent`；Java 提供业务入口、用户身份、知识库授权和流式结果转发，前端不直接访问 Python。

**前置条件：** P3-20、P3-22、P3-25、P3-29、P3-30。

**实施内容：** 实现知枢 Agent 的系统提示词、检索工具、上下文构造、引用格式、无答案策略、敏感内容防护和多轮对话。支持用户选择知识库、模型和检索策略，但不能绕过权限和配额。

**交付与验收：** 用户可以提出问题并获得带引用的回答；检索不到依据时明确回答不确定；知识库中的 Prompt 注入不能覆盖系统规则。

### P3-32 建立 RAG 评测、反馈和调优闭环

**服务归属：** Python 负责评测集执行、检索指标和模型回答分析；Java 负责用户反馈入口、反馈权限、通知和管理端展示。

**前置条件：** P3-30、P3-31。

**实施内容：** 建立问题、标准答案、期望引用、禁止回答和权限隔离样例；统计召回率、引用命中率、答案可用率、幻觉率、延迟和 Token 用量；将用户的“有帮助/无帮助/引用错误/泄露风险”关联到具体 Run。

**交付与验收：** 检索策略和 Prompt 的修改可以比较前后效果；线上反馈可以定位到分块、模型、重排或回答步骤。

### P3-33 建设知枢用户端和管理端工作台

**服务归属：** `knowhub-ui` 和 `rookie-ui` 通过 Java API 访问；Java 聚合 Python 的状态和结果，Python 不承担浏览器鉴权和页面路由。

**前置条件：** P3-26、P3-31、P3-32。

**实施内容：** 业务端提供知识库选择、对话、流式输出、引用展开、重新生成、复制、导出、历史管理和反馈；管理端提供模型、配额、检索策略、敏感词、评测集和索引状态管理。

**交付与验收：** 处理中、空数据、无权限、索引失败、模型失败、引用缺失和网络中断均有明确界面；管理端不能查看用户私人 Key 或无权知识内容。

### P3-33A 实现 AI 日报生成计划、生成链路和前台展示

**服务归属：** Java 管理日报计划、日报业务记录、展示权限和通知关联；现有 `sys_job` 负责可配置触发；Python `knowhub-agent` 负责数据整理、Prompt 组装、模型调用和生成 Run；前端分别提供管理端配置页和业务端日报入口。

**前置条件：** P3-04、P3-05、P3-13、P3-18、P3-20、P3-23；现有 `SysJobScheduler`、`sys_job_log`、系统通知和 Markdown 展示链路可复用。

**实施内容：** 将 AI 日报设计为“日报配置组 + 多条生成计划”，不再使用单一全局时间、单一主题和单一提示词。配置组显式保存每日生成份数字段，并维护与数量对应的生成时间槽；每条计划至少包含名称、主题、主题提示词、生成时间或 cron、数据来源范围、目标用户/通知范围、模型策略、失败重试和保留策略。保存时校验有效时间槽数量与每日生成份数一致，并校验重复时间、无效主题和系统上限。

Java 通过现有 `sys_job` 动态任务触发日报计划，不能新建另一套 `@Scheduled` 调度中心。触发时以“计划 ID + 业务日期 + 时间槽”建立幂等任务，调用 `knowhub-agent` 异步生成；Python 返回标题、摘要、Markdown 正文、来源摘要、Run ID、模型引用、Token/耗时和失败信息。Java 保存日报计划快照和日报记录，状态至少包括待生成、生成中、成功、失败和已删除，支持人工立即执行、失败重试和单期删除。

日报第一版优先聚合 KnowHub 内部数据，包括当天发布/更新的博客、文章、章节、项目、资源、审核动作和学习记录；外部新闻、RSS、第三方 API 作为后续数据源，不阻塞内部日报闭环。日报正文默认只读，后台不提供逐字编辑；如果后续需要人工校对，新增独立审核/发布状态。

**前置复用：** 日报配置复用 Java 系统权限和配置规范；定时触发复用 `SysJobScheduler`；通知复用 `SysNotice` 及通知分组；正文复用现有 Markdown 存储/渲染；模型调用复用 Model Gateway 和动态凭据策略；长时间生成由 Python Worker 承载，不占用 Java 调度线程。

**交付与验收：** 管理员可以创建、编辑、启停和立即执行多条日报计划；配置页面能明确显示每日预计生成份数、每份时间和主题；同一计划同一业务日期不会重复生成；单条计划失败不会阻断其他计划；生成结果可在业务端按主题/日期分页查看；日报可发送通知但通知不承载正文；日志、Prompt、日报内容和错误信息中均不泄露任何模型 Key 或无权数据；Java 多实例部署前明确单机调度边界和防重策略。

## 8. 面试 Agent、Skill 管理与自定义 Agent

### P3-34 建立面试 Agent 的动态出题、难度、用户画像与复习体系

**服务归属：** 面试 Agent 的题库策略、流程和运行逻辑由 Python 管理；Java 负责用户资料、岗位信息的业务接口和前端权限。

**前置条件：** P3-19、P3-20、P3-22、P3-24。

**实施内容：** 以项目文档中既定的“简历 + 难度档 + 用户画像”三维驱动方式为主，支持技术面、项目面、行为面和综合面。面试 Agent 同时支持模拟面试和学习复盘/复习测试两种模式；两种模式共享 Agent 会话框架、知识素材、评分规则和用户画像，但在出题范围、交互方式和报告内容上区分开。

#### 难度三档保持与项目文档一致

- **简单档：** 以简历涉及技术栈的基础八股为主，进行概念辨析、原理简述和用法对比，强调知识覆盖和基础扎实度，不深挖项目细节。
- **中间档：** 结合简历项目经历，深挖业务设计、技术选型理由、架构权衡、难点取舍和个人实际贡献，重点考察用户能否讲清楚做过的事情。
- **困难档：** 在中间档基础上加入项目扩展和场景化八股，例如规模放大、流量突增、依赖故障和新增能力，并追问用户如何迁移知识解决问题。

三档使用同一 Agent 会话框架，主要通过系统提示词、出题策略、追问深度、场景复杂度和评分标准差异实现，不要在代码中复制三套 Agent。

#### 题库的正确定位：素材库和规则库，不是固定题目硬编码

项目文档明确“不做题库硬编码”。因此，本计划中的“题库”应实现为可供 LLM 动态出题的知识与规则集合，至少包含知识点、岗位/方向、标签、难度适用范围、参考资料、题型模板、考察目标、评分点、常见误区、追问策略和来源版本。可以保留少量固定样题用于示例、评测和回归测试，但模拟面试和学习复盘不能只做固定题目随机抽取。

生成出来的题目、题目所依据的素材、提示词版本、画像快照和评分规则需要在一次面试或复习测试中固化保存，保证历史记录可回放；素材库后续修改不能改变过去已经生成的题目和报告。

#### 用户学习记录

每次用户学习某个知识点或素材、发起学习复盘、浏览生成题目、作答、跳过、查看解析、获得评分或标记“已掌握”都形成学习记录。记录至少包含用户、知识点/素材版本、学习时间、作答结果、得分、耗时、错误知识点、用户自评信心和复习次数。学习记录属于用户隐私数据，管理员只能查看聚合统计或经过授权的处理结果，不能默认查看用户的完整作答内容。

#### 用户画像作为跨场景长期记忆

用户画像不是简单的聊天上下文，也不是只保存当天的错题。它是面试 Agent 的长期记忆，至少汇总三类来源：模拟面试的提问序列、用户作答、Agent 评价和薄弱点；学习复盘/复习测试的考察范围、正确率和反复出错知识点；用户主动填写的真实面试回录。画像采用追加记录和可重算摘要的方式，保留来源与时间，避免直接覆盖导致无法解释。

画像需要反哺后续行为：对已掌握领域减少重复提问，对薄弱领域加深追问，对真实面试中踩过的坑进行针对性复测，并给出下一步练习和建议难度。短期会话记忆、题目快照和长期用户画像必须分开建模。

#### 基于历史记录的复习测试

复习测试保留项目文档中的“用户自主选择考察范围”作为标准入口，同时增加“根据今天学习历史自动推荐”入口。用户可以指定 MySQL 索引、Spring AOP、项目鉴权设计等范围；如果用户不指定范围，系统根据当天学习过的知识点和历史画像自动生成范围。

选题和出题优先覆盖答错、低分、低信心、长时间未复习、同一知识点反复出错和真实面试中暴露的问题，同时控制题目重复率、知识点覆盖率和测试时长。第一版采用可解释的规则策略，后续再增加间隔重复、掌握度模型或个性化难度调整。测试过程中不提前展示参考答案；提交后展示正确性、评分点、解析、错因和下一次建议复习时间，并把结果写回用户画像。

#### 模拟面试与复习测试的边界

模拟面试是 Agent 主导、覆盖简历全领域的连续对话，强调追问、表达、项目讲解和场景迁移；学习复盘/复习测试是用户框定范围或系统根据学习历史推荐范围，Agent 在范围内动态出题，强调“刚学完是否真正记住”。复习测试不应简单复用模拟面试的随机题目，而要保存选题依据、素材来源、知识点覆盖、画像快照和学习历史快照，保证用户能理解“为什么今天复习这些题”。

**交付与验收：** 简单/中间/困难三档行为与项目文档一致；每次模拟面试或复习测试都绑定提示词、素材、题目快照、画像快照和评分规则版本；用户可以查看学习日历、知识点掌握度、错题和复习建议；系统可以根据用户指定范围或当天学习历史生成一套可完成的复习测试，并在提交后更新用户画像和下一次复习计划；管理员可维护素材和规则但不能读取用户私人简历、长期画像明细和完整学习作答内容。

**前置条件：** P3-04、P3-11、P3-53、P3-55。

**实施内容：** 按组织、项目、仓库、分支、环境和用户权限过滤数据；自动脱敏环境变量、Token、证书、Cookie、密码和日志中的密钥；限制外部连接的网络和资源范围。

**交付与验收：** 用户不能看到无权仓库、构建、日志、制品和部署环境；脱敏前后都有安全测试；同步凭据不能被管理员通过普通页面读出。

### P3-57 实现 CI/CD 流程化检索 Agent

**前置条件：** P3-29、P3-30、P3-55、P3-56。

**实施内容：** 支持“某次发布为什么失败”“哪些提交影响了这个接口”“最近一次成功部署是什么版本”“这个 Job 的失败是否是已知问题”等问题。回答必须串联 Commit、PR、Pipeline、Job、日志、部署和相关文档，并给出证据链。

**交付与验收：** 对关键问题有固定评测集；回答能区分事实和推断；用户无权访问的数据不会进入检索结果或回答上下文。

### P3-58 将 CI/CD 检索接入工具和发布门禁

**前置条件：** P3-24、P3-25、P3-57。

**实施内容：** Agent 可以查询构建状态、失败日志、变更摘要和部署记录；发布前可自动检查测试、质量、依赖、迁移和健康状态。部署、回滚、重跑构建等有副作用动作只能生成建议或等待人工确认。

**交付与验收：** Agent 不会直接越权部署；每次门禁有规则版本、证据、通过/失败原因和人工确认记录。

## 12. CI/CD 发布、运维和质量闭环

### P3-59 建立 Java、双前端和 Python 服务的 CI 基线

**前置条件：** P3-01；Python `knowhub-agent` 可以先以最小健康检查项目接入。

**实施内容：** Java 后端执行 Maven 编译、单元测试、集成测试、数据库脚本校验、安全扫描和打包；Python `knowhub-agent` 执行依赖锁定、单元测试、协议测试和镜像构建，Agent Runtime、检索回归等测试随着功能接入；两个前端执行 package 脚本、类型检查、构建、组件测试、路由检查和依赖扫描。统一注入环境变量和敏感配置，产物带 Commit/版本标识，并设置分支合并门禁。四个工程都必须纳入流水线。

**交付与验收：** 任何核心测试、构建、迁移校验或安全门禁失败时不能进入下一环境；产物有版本号和可追溯 Commit。

### P3-60 建立分环境部署、健康检查和回滚骨架

**前置条件：** P3-59、P3-01。

**实施内容：** 先区分开发、测试、预发布和生产环境，分别管理 Java、Python、两个前端和基础配置；模型 Key、数据库、向量索引和外部连接在对应模块接入时再纳入。发布顺序应保证 Java 与 Python 内部协议兼容，空壳服务也要能执行健康检查、冒烟测试和失败回滚；后续再加入数据库迁移、索引迁移和 Agent 数据兼容检查。

**交付与验收：** 数据库迁移、索引迁移、后端、前端和配置更新有明确顺序；可以回滚到上一稳定版本；回滚不会让旧版本读取不了数据。

### P3-61 建立 Agent、RAG、密钥和互动质量大盘

**前置条件：** P3-11、P3-18、P3-22、P3-32、P3-45、P3-57。

**实施内容：** 监控登录风险、密码找回、Key 使用、模型健康、Token 用量、Agent 失败率、RAG 引用命中率、索引失败、私信滥用、反馈处理时长和 CI/CD 失败率。

**交付与验收：** 关键指标有阈值、告警和责任人；告警信息经过脱敏；能够从告警跳转到 Run、任务、Pipeline 或反馈记录。

### P3-62 完成安全、压测、灾备和全链路验收

**前置条件：** 本文所有功能任务完成到可测试状态。

**实施内容：** 执行越权、密钥泄露、Prompt 注入、SSRF、XSS、恶意文件、暴力登录、私信滥用、模型超时、索引重建、队列堆积、数据库恢复、KMS 轮换和 CI/CD 故障演练。

**交付与验收：** 形成第三阶段发布报告、风险清单、回滚手册、备份恢复记录、密钥轮换记录、性能基线和用户操作文档；未关闭的高风险问题不得正式发布。

## 13. 任务依赖主线

```text
四工程 CI 基线与开发/测试部署骨架
  -> 现有 Java 身份/权限/Redis/通知/文件能力
  -> Python knowhub-agent 与 Java 内部调用协议
  -> Agent 专属身份上下文、数据归属和任务状态
  -> Python Model Gateway、凭据租约和调用控制
  -> Python Agent Runtime、会话、工具白名单和 Run 审计
  -> Python 数据解析、分块、全文/向量索引和 Agent ACL
  -> Java 对外聚合 API + Python 混合检索和引用
  -> 知枢 RAG-Agent、AI 日报、面试 Agent、Skill 和自定义 Agent
  -> Java 侧私信/通知/反馈与 Agent 事件衔接
  -> CI/CD 数据同步、流程化检索和发布门禁
  -> Java/Python/前端联合测试、监控、灾备和正式发布
```

以下事项不能提前直接开放：

- 没有 Model Gateway 时，不要把供应商 SDK 直接写入业务 Agent。
- 没有 KMS/HSM、脱敏和凭据引用时，不要开放用户私人模型 Key。
- 没有文档 ACL 时，不要把个人文件接入 RAG。
- 没有 Agent 版本和 AgentRun 时，不要允许自定义 Agent 正式发布。
- 没有工具白名单、步数限制和人工确认时，不要开放写库、发私信、部署或命令执行。
- 没有 CI/CD 权限隔离和日志脱敏时，不要把构建日志、环境变量和部署信息接入检索。
