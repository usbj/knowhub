## 1. 文档定位与阅读约定

KnowHub 是在 rookie 后台管理基础框架之上持续建设的综合知识库系统。本文件回答以下问题：

- KnowHub 要解决什么问题；
- 当前代码已经实现了什么；
- 现有模块之间如何划分边界；
- 第三阶段为什么引入独立的 `knowhub-agent`；
- AI 日报、知枢 RAG-Agent、面试 Agent、Skill 和自定义 Agent 如何共存；
- 哪些内容属于后续规划，不能被误认为已经实现。

文中状态使用以下含义：

- **已实现**：代码、接口或前端页面已经存在，并且可以在现有工程中找到对应实现；
- **部分实现**：底层能力已存在，但业务闭环、前台入口或边界仍不完整；
- **第三阶段规划**：已进入后续建设范围，但当前不应视为可用功能；
- **后续预留**：只保留方向，不作为第三阶段的必交付内容。

## 2. 项目背景与建设目标

### 2.1 项目背景

高校学生实验室、中小企业和小型组织通常同时存在以下问题：知识分散在博客、文档、网盘、代码仓库和聊天记录中；项目资料缺少统一归档；资源难以检索和复用；内容审核、权限和通知依赖人工沟通；已有系统即使保存了数据，也不能帮助用户完成学习、复盘和问题分析。

KnowHub 的目标不是单纯做一个文章发布站，而是把知识内容、项目资产、资源文件、组织互动和后续 AI 能力放在同一个可管理的业务底座上。

### 2.2 目标用户

- 实验室或组织中的普通成员：浏览、学习、搜索、收藏、评论、参与项目和使用 Agent；
- 内容作者和项目成员：创建、编辑、上传、提交审核和维护自己的内容；
- 审核人员：处理内容审核、下架、驳回和治理记录；
- 系统管理员：管理用户、角色、菜单、系统配置、通知、定时任务和运营数据；
- 第三阶段的 Agent 使用者：使用知枢 RAG-Agent、面试 Agent、Skill 和自定义 Agent。

### 2.3 建设目标

当前建设目标分为四层：

1. **内容沉淀**：支持博客、学习文档、章节、项目资料、资源和文件统一管理；
2. **组织治理**：支持用户、角色、权限、审核、通知、日志、文件安全和定时任务；
3. **知识使用**：支持全文检索、标签检索、推荐、历史记录、评论和后续混合检索；
4. **智能扩展**：通过独立的 `knowhub-agent` 提供 RAG、面试训练、Skill、自定义 Agent、模型接入和 AI 日报。

当前阶段不建设计费、套餐、支付和商业化计量体系。模型调用可以记录调用次数、Token、耗时和失败情况，但这些数据只用于限额、监控和质量分析。

## 3. 当前实现状态

### 3.1 工程实际组成

当前仓库不是只有 rookie 基础框架，而是由以下部分共同组成：

- `rookie-admin`：Spring Boot 启动和后端入口；
- `rookie-common`：统一返回、异常、分页、缓存、工具和公共实体；
- `rookie-framework`：Spring Security、Token 校验、日志切面、异步和框架配置；
- `rookie-system`：用户、角色、菜单、字典、系统配置、通知、日志、在线用户和定时任务；
- `knowhub`：KnowHub 业务后端，包含博客、文章、章节、项目、资源、标签、评论、历史、审核和文件存储等；
- `rookie-ui`：后台管理端及 KnowHub 管理端页面；
- `knowhub-ui`：面向普通用户的业务端页面；
- `sql/knowhub.sql` 及增量 SQL：数据库结构、菜单、字典和业务初始化脚本；
- `doc/`：产品设计、接口、开发日志、专项设计和第三阶段规划。

第三阶段新增的 Python 服务名称统一为 `knowhub-agent`。当前仓库中尚未存在完整的 Python Agent 服务实现，因此本文中有关 Agent 的内容均属于规划，除非另有明确说明。

### 3.2 已实现的系统基础能力

以下能力属于现有 rookie 基础框架，已经在 Java 后端和 `rookie-ui` 中形成可复用基础：

- 用户管理、角色管理、菜单管理、按钮级权限和动态路由；
- JWT 登录认证，前端请求通过 `Token` 请求头传递令牌；
- Spring Security 方法级权限控制，以及管理员角色的现有兜底逻辑；
- 字典、系统配置、配置缓存和按配置项读取；
- 消息通知、通知分组、我的通知、已读和确认；
- 操作日志、错误日志、请求/异步/定时任务的错误记录；
- Redis 缓存、MyBatis、PageHelper、统一返回和全局异常处理；
- 动态定时任务：任务元数据保存于 `sys_job`，通过 `SysJobScheduler` 动态注册 `CronTrigger`，支持启停、编辑、立即执行和执行日志；
- 在线用户和在线状态查询；
- 文件对象管理及本地/S3 兼容存储后端。

注册入口已经存在，但邮箱验证、邮箱找回密码、多端会话治理和更完整的登录风险控制仍属于第三阶段补强内容，不能将“已有注册接口”理解成完整的邮箱账号体系。

### 3.3 已实现的 KnowHub 业务能力

当前 `knowhub` Java 模块已经存在以下业务实现：

- **博客**：后台管理、前台搜索/推荐/详情、创作、发布/撤回、审核流水、点赞、收藏、评分、标签、浏览记录和 Markdown 内容展示；
- **文章与章节**：文章管理、章节结构、前台文档学习、章节正文阅读、搜索命中章节提示、等级/越级锁定和作者侧维护；
- **标签**：标签管理、内容关联、热门标签和跨博客/文章的标签聚合；
- **项目**：项目管理、项目展示、成员、邀请、项目文件树、源码包、项目搜索/推荐和项目文档；
- **资源**：网站资源和文件资源、分类、搜索、推荐、相关资源、上传、下载、点赞、收藏、评分和资源审核；
- **评论与互动**：博客、文章、项目、资源等内容的评论/回复，以及回复场景的站内通知；
- **历史记录**：用户浏览历史和相关前台入口；
- **审核治理**：博客、文章、项目、资源等对象的发布、待审、通过、驳回、撤回、下架和审核流水；
- **审计业务**：实验室主体、经费流水、借用/归还、逾期处理、周期报表和相关通知；
- **文件存储**：上传令牌、对象确认、PUBLIC/PRIVATE 访问、代理或直链模式、文件绑定、迁移和垃圾回收。

这些能力不应在第三阶段重新设计一套平行实现。Agent 需要读取文章、博客、项目、资源、文件和审核数据时，必须通过现有 Java 业务接口和权限边界接入。

### 3.4 当前尚未实现或仅有基础的功能

以下内容目前不应标记为已完成：

- 完整的邮箱验证、通过邮箱找回密码和登录风险控制；
- 独立的 `knowhub-agent` Python 服务；
- Model Gateway、多供应商模型目录、动态 Key 注入和用户私人 Key 强隐藏；
- Agent 会话、短期记忆、Agent 专属长期用户画像和 Run 审计；
- 向量数据库、Embedding、混合检索、重排和 RAG 引用链；
- 面试题库素材/规则库、复习测试和面试训练报告；
- Skill 管理、自定义 Agent、工具编排和 Agent 发布回滚；
- AI 日报的后台多计划配置、自动生成、日报记录和完整前台日报页面；`knowhub-ui` 当前只有首页静态占位卡片，不属于已实现的日报功能；
- 用户私信、实时消息和断线恢复；
- CI/CD 数据同步、流程化检索和发布门禁；
- 第三阶段针对 Agent 的质量大盘、压测、灾备和安全验收。

## 4. 系统边界与总体架构

### 4.1 Java 后端边界

Java 后端继续作为浏览器请求的入口和 KnowHub 业务数据的权威边界，负责：

- 浏览器认证、基础角色权限和资源所有权校验；
- 用户、文章、博客、章节、项目、资源、评论、通知、文件和审核数据；
- 业务端和管理端 API；
- 现有 MyBatis、Redis、系统配置、动态定时任务和通知能力；
- AI 日报的产品记录、后台配置、展示接口和业务权限；
- 调用 `knowhub-agent` 并向前端转发结果、流式事件和错误状态。

Java 不负责实现 Agent 循环、模型供应商 SDK、Embedding、向量召回和长期记忆召回。

### 4.2 `knowhub-agent` 边界

`knowhub-agent` 是独立的 Python Agent 后端服务，负责：

- Agent Runtime、会话运行、工具调用和流式事件；
- Model Gateway、模型供应商适配、Embedding 和重排；
- 知识库解析、切片、向量索引、召回编排和引用证据；
- 短期上下文和按 `userId + agentId` 隔离的长期记忆；
- 知枢 RAG-Agent、面试 Agent、Skill 和自定义 Agent；
- 长时间 Run、索引任务、模型调用和 Agent 质量追踪。

浏览器不能直接访问 `knowhub-agent`。Java 需要传递经过验证的用户、Agent、会话、资源范围和请求追踪上下文，Python 不信任浏览器直接传入的 `userId`、权限或知识库 ID。

### 4.3 数据流与所有权

```text
用户浏览器
   ↓ Token
Java 后端
   ├─ 认证、权限、业务数据、文件和日报记录
   └─ 内部授权上下文
          ↓ HTTP
knowhub-agent
   ├─ Agent Runtime、Model Gateway、记忆和检索
   └─ Agent Run、索引任务、向量索引和检索追踪
          ↓
模型供应商 / 向量数据库 / 外部 CI/CD 数据源
```

原始文章、博客、项目、资源和文件归 Java 业务域所有。向量索引属于 `knowhub-agent` 的派生索引，不是新的原始数据源；原文修改、删除和权限变化时，必须由 Java 触发或通知 Python 更新索引。

## 5. 已实现的基础与业务模块

### 5.1 系统管理底座

系统管理端围绕“用户—角色—菜单—权限—字典—通知—日志—定时任务”组织。管理端功能包括用户和角色维护、菜单权限配置、字典数据维护、系统参数配置、通知发布、日志查询、在线用户和动态定时任务管理。

#### 用户、角色、菜单与权限

- 用户管理支持用户列表、详情、创建、编辑、状态调整和删除；用户通过角色获得菜单和按钮权限；
- 角色管理支持角色状态、默认角色、角色菜单绑定和权限点维护；
- 菜单管理支持目录、菜单和按钮权限的层级结构，前端根据用户路由权限动态生成管理端菜单；
- 接口层使用 `@PreAuthorize` 做按钮级权限判断，业务对象还需要在 Service 层补充作者、成员、管理员和资源可见范围校验；
- `admin` 角色存在现有的全部权限兜底逻辑，但这不代表第三阶段的 Agent 可以无条件读取所有用户私有数据。

#### 字典与系统配置

字典用于状态、类型、动作和枚举类配置，例如审核状态、资源类型、文件业务类型和项目类型；系统配置用于运行时开关、阈值、访问模式和任务参数。两者需要区分：可枚举选项走字典，运行时参数走系统配置，密钥原文不能放进普通配置值。

#### 通知中心

系统通知包含通知内容、发布范围、通知分组、目标用户、已读和确认状态。管理员可以创建、编辑、发布、撤回和删除通知；用户端可以查看自己的通知、统计未读、标记已读、全部已读和确认需要确认的通知。通知适合承载公告、审核结果、评论回复、任务完成和系统告警，不适合保存私信正文或大段 AI 日报内容。

#### 日志与在线状态

操作日志记录管理员和业务操作的请求信息、操作人、耗时和结果；错误日志接收请求、异步和定时任务错误，并支持从操作日志关联查看。在线状态由 Token 校验后的活跃时间和 Redis 数据支撑，前端通过心跳补充挂机场景。日志中不得写入密码、API Key、完整 Token、Prompt 中的敏感内容或私信正文。

动态定时任务已经具备以下约束：

- cron 使用 Spring 六段式表达式；
- 保存前校验 Bean、方法和白名单包；
- 任务可以动态启用、停用、编辑和立即执行；
- 每次执行写入 `sys_job_log`；
- 当前是单机调度语义，多实例部署需要补充分布式锁或外部任务平台。

后续 AI 日报必须复用这套调度能力，不能再为日报另外实现一套互相独立的 Java 定时框架。

### 5.2 知识内容模块

博客和文章都是知识沉淀内容，但使用场景不同：博客偏向独立文章、公开浏览和创作互动；文章/章节偏向有层级结构的学习文档、路线和速成内容。标签是跨内容模块的独立基础能力，负责分类、筛选、热门统计和推荐辅助。

内容模块统一遵循以下状态和边界：

- 后台负责内容管理、审核和治理；
- 前台负责公开浏览、搜索、推荐、学习和用户创作；
- 已发布内容的修改必须服从当前审核状态机；
- 审核动作和关键状态变化要保留流水，不能只覆盖主表最后状态；
- Markdown 保存原文，前台按统一渲染链路展示；
- 前台详情接口和后台管理接口按调用面分离，但 Service/Mapper/领域对象按内容模块复用。

#### 博客功能

博客面向单篇知识内容、经验总结、实验记录和技术文章。作者可以创建草稿、编辑标题/摘要/封面/正文/标签/可见性和评论设置，保存后提交发布；如果审核开关开启，发布会进入待审核状态，否则可以直接进入已发布状态。已发布博客需要先撤回才能修改，避免绕过审核直接修改线上内容。

前台博客功能包括：

- 首页或博客导航中的推荐列表；
- 按关键词搜索标题、摘要和正文；
- 按标签筛选和查看热门标签；
- 按最新、热度或相关度排序；
- 查看详情、作者信息、发布时间、浏览量、评分、点赞和收藏状态；
- Markdown 正文、代码块、目录和图片展示；
- 登录用户点赞、收藏、评分、评论、回复和问题反馈；
- 查看自己的创作、草稿、待审、驳回和已发布内容。

后台博客功能包括列表筛选、详情查看、作者和状态管理、发布/撤回、审核、下架、删除、审核流水查看和互动数据查看。审核员不能审核自己提交的内容，审核动作需要记录操作人、动作、意见和时间。

#### 文章、章节与学习文档

文章适合承载一个有学习目标的文档集合，章节负责集合内部的顺序、标题、正文和发布状态。文章与博客共用标签、审核、收藏/点赞和 Markdown 内容能力，但文章前台额外强调章节目录、学习进度和章节阅读。

文章/章节的主要流程是：

1. 作者创建文章并填写标题、简介、封面、标签、可见等级和前言；
2. 作者进入章节管理页，新增、编辑、排序和删除章节；
3. 章节分别保存草稿或发布，文章整体发布状态与章节可读状态共同决定前台展示；
4. 用户在文档列表搜索或按标签筛选，进入详情页查看文章简介和章节目录；
5. 用户选择章节阅读，系统校验用户等级/访问权限，允许时返回正文，否则返回锁定状态和原因；
6. 搜索命中章节正文时，列表需要标明命中的章节，用户可以直接跳到对应章节阅读。

学习路线和速成文档属于文章/章节的产品化使用场景，不应再单独建设一套内容存储模型。学习路线可以通过文章、章节、外部链接、项目实践和路线说明组合形成；速成文档则通过章节顺序和学习提示形成连续学习内容。

#### 标签、搜索与推荐

标签是跨博客、文章和后续项目/资源的公共分类能力。后台负责标签创建、编辑、启停、合并和规范命名；前台用于筛选、聚合和推荐。当前关键词检索主要使用 MySQL FULLTEXT ngram 和标签关系，项目/资源等模块再叠加各自的状态、分类和权限条件。

推荐目前以规则和统计为主，包括发布时间、浏览量、点赞、收藏、评分、标签偏好和内容类型等因素。它不是第三阶段 RAG 的替代品：推荐解决“给用户展示哪些内容”，RAG 解决“根据问题召回哪些片段并生成回答”。

### 5.3 项目与资源模块

项目模块用于展示项目说明、状态、成员、邀请、项目文件树和源码包；资源模块用于管理网站资源和文件资源，并提供分类、搜索、推荐、相关资源、下载、点赞、收藏和评分。

#### 项目模块功能

项目创建者可以维护项目名称、简介、正文、封面、项目类型、项目状态、版本信息、标签、成员和项目文件。项目成员可以通过邀请加入项目，项目详情根据成员关系和项目可见范围展示相应内容。

项目后台和业务端需要区分两个操作面：

- 项目作者/成员维护自己有权编辑的草稿和项目资料；
- 管理员负责项目审核、上下架、违规处理、状态归档和权限兜底；
- 项目文件提供文件树、单文件下载和源码压缩包下载；
- 项目文档可以关联文章/章节，但不能把项目文档复制成另一份独立正文；
- 项目详情可以展示成员、邀请、评论、评分、点赞、收藏、浏览量和相关项目。

项目状态主要用于成果展示和归档，例如准备中、开发中、比赛中、已结项、已归档和已下架。它不等同于完整研发管理状态，任务拆分和迭代看板属于后续协作开发模块；构建、部署和日志检索属于第三阶段的 CI/CD 数据接入能力。

#### 资源模块功能

资源分为网站资源和文件资源。网站资源保存名称、简介、分类、链接和可见范围；文件资源保存文件对象、类型、大小、下载信息和资源描述。两类资源共用分类、审核、标签、互动和推荐规则，但访问行为不同：网站资源跳转外部地址，文件资源需要生成下载链接或由后端代理下载。

前台资源流程包括搜索、分类筛选、类型筛选、热门/最新排序、分页、详情、相关推荐、网站访问、文件下载、点赞、收藏、评分和我的收藏。后台负责资源分类树、资源 CRUD、审核、发布/撤回、删除、文件替换限制和资源访问权限。

资源和项目的发布内容必须满足 `PUBLISHED` 等前台可见条件；草稿、待审核、驳回和已删除资源不应出现在公开搜索和推荐结果中。已发布资源更换源文件需要先撤回，避免用户继续访问旧版本时出现内容不一致。

项目和资源都可以成为后续 RAG 的数据源，但接入 RAG 时需要区分：

- 公开展示内容可以进入公共知识库索引；
- 未发布、私有或仅成员可见内容必须携带 ACL；
- 项目源码包和私有文件不能因为被向量化就变成可公开检索内容；
- Python 侧返回片段前必须执行资源范围过滤，前端隐藏不是权限控制。

### 5.4 审核、评论、通知与文件

审核、评论、通知和文件存储不是 AI 模块的附属功能，而是所有后续能力复用的业务底座：

- 审核流水决定哪些内容可以进入公开推荐和公共知识库；
- 评论回复通过现有通知能力形成互动闭环；
- 通知用于公告、审核结果、回复、任务完成和系统告警；
- 私信未来需要独立的消息正文和会话模型，不能把私信内容直接塞进公告通知表；
- 文件上传统一经过类型、大小、对象状态和访问模式校验，简历、Skill 包、知识库附件和日报附件应复用文件底座。

#### 审核与治理流程

内容审核至少包含草稿、待审核、已通过/已发布、已驳回、已撤回、已下架和已删除等语义。作者提交发布时产生提交流水；审核员通过或驳回时记录意见；作者撤回或管理员下架时记录治理动作。审核开关可以按业务模块配置，但状态机不能因为开关变化而遗留无法处理的待审数据，需要通过已有对账任务收口。

审核权限包括“查看待审列表、查看详情、通过、驳回、下架、删除和查看流水”，不能仅依赖前端按钮隐藏。作者、项目成员、资源所有者和管理员的编辑范围不同，Service 层必须再次校验归属和状态。

#### 评论与内容互动

评论功能挂载在博客、文章、项目和资源详情页，支持发表评论、回复、作者身份标识、精选/可见控制、评论开关和评论配图。回复其他用户时可以通过现有通知中心提醒被回复者；通知失败不能回滚已经成功保存的评论。评论正文继续使用 Markdown 渲染约定，图片通过文件对象引用，不把绝对存储地址直接写入业务内容。

#### 文件存储流程

文件上传不是直接把二进制流塞入业务接口，而是：

1. 前端提交业务类型、文件名、大小和内容类型，后端校验白名单；
2. 后端创建待确认对象并返回预签名或代理上传地址；
3. 前端上传到 RustFS/S3 兼容存储；
4. 后端确认对象真实大小、类型和 ETag，状态从 PENDING 变为 CONFIRMED；
5. 业务表只保存对象 ID 和绑定关系，下载/回显根据 PUBLIC、PRIVATE 和访问模式生成地址；
6. 超时未确认、软删和迁移失败对象由文件 GC/迁移任务处理。

博客图片、项目源码包、资源文件、评论图片、简历、Skill 包、知识库附件和日报附件都应复用该流程，只通过 `businessType`、访问级别和业务绑定区分用途。

#### 审计业务

审计模块已经包含主体、经费流水、借用/归还、逾期处理和周期报表等业务实现。周期报表可以按周/月由 `sys_job` 触发，也支持对已结束周期手动重算；报表生成后可以通知负责人。该模块与操作日志不同：操作日志记录“谁调用了什么接口”，审计模块记录“实验室主体发生了什么业务事项”。

## 6. 前台、后台与交互入口

### 6.1 `knowhub-ui` 业务端

当前业务端已经包含首页、博客、文章/章节、项目、资源、搜索、浏览历史、通知、个人中心、登录和注册等入口。第三阶段在此基础上增加：

- 知识库和知枢 RAG-Agent 工作台；
- 面试 Agent、简历、题库学习和复习测试；
- Skill 浏览、挂载和自定义 Agent；
- AI 日报首页卡片、日报列表和详情；
- 私信、会话列表和消息提醒；
- 模型 Key、隐私、账号安全和长期记忆管理入口。

当前业务端的主要使用链路是：

- 游客浏览首页、公开博客/文章/项目/资源和搜索结果；
- 登录用户进入详情后获得点赞、收藏、评分、评论、历史和下载等能力；
- 作者从个人中心进入博客、文章、项目或资源创作页，保存草稿后提交发布；
- 内容进入审核时，作者可以在个人中心查看状态、驳回意见和审核流水；
- 项目成员通过邀请加入项目，成员关系决定项目资料和文件的可见范围；
- 用户从首页、标签、搜索、推荐和历史记录之间跳转，详情页使用统一的 Markdown、评论和互动组件。

第三阶段的 Agent 工作台不能直接把 Python URL 暴露给浏览器，应由业务端调用 Java 聚合接口。前端需要能够表示空状态、索引中、生成中、无权限、模型失败、引用缺失、网络中断、任务取消和重试中等状态。

### 6.2 `rookie-ui` 管理端

当前管理端已经包含系统管理、KnowHub 内容管理、审核、文件、项目、资源、标签、审计和定时任务页面。第三阶段增加或扩展：

- 模型供应商和模型目录；
- Agent、知识库、索引和评测管理；
- AI 日报生成计划管理；
- Skill 审核、版本和挂载策略；
- 自定义 Agent 的审核、发布和回滚；
- 私信举报、反馈流转和 Agent 质量反馈；
- CI/CD 连接、同步任务、检索权限和发布门禁。

管理端的职责是“配置和治理”，不是替用户完成所有业务操作。管理员可以配置系统参数、动态任务、模型目录、日报计划、知识库授权、审核策略和安全策略，但不应默认查看用户私人模型 Key、私人长期记忆、私信正文或无权访问的知识内容。需要查看质量数据时，应优先查看脱敏统计、Run 摘要和引用元数据。

### 6.3 前台与后台不是数据边界

“前台”和“后台”只描述使用入口，不代表数据由两个系统重复维护。同一内容模块的业务规则应集中在 Java Service 层；前台和后台只通过不同 Controller、权限和 VO 暴露不同调用面。Agent 也不能绕过 Java 的业务授权直接从数据库读取内容。

## 7. 跨模块技术规则

### 7.1 认证与权限

浏览器请求继续复用现有 `TokenVerifyFilter`、Redis 用户上下文、`SecurityContext` 和 `@PreAuthorize`。第三阶段只为 Agent、知识库、Skill、Run、日报计划和私信补充资源级权限，不重写用户角色体系。

Java 调用 `knowhub-agent` 时传递短生命周期、可校验的内部授权上下文。Python 不直接解析浏览器 Token，也不接受未经 Java 验证的用户身份或权限字段。

### 7.2 数据存储

Java 数据库继续使用当前 MyBatis Mapper/XML、实体、VO、Quarry、PageHelper 和 `sql/*.sql` 习惯。Python 服务维护自己的 Agent 运行数据、记忆、索引任务和向量索引，不直接写 Java 业务表。

AI 日报是面向用户展示的产品内容，日报计划、日报记录、生成状态、展示权限和删除策略归 Java 业务域；模型调用过程、Prompt 快照、模型引用、Token 和 Run 追踪归 `knowhub-agent`，两边通过报告 ID 和 Run ID 关联。

### 7.3 搜索与混合检索

当前已实现的关键词检索主要复用 MySQL FULLTEXT ngram、标签和内容模块已有查询逻辑。ngram 是分词/全文检索实现，不等同于 BM25。

第三阶段先采用以下过渡边界：

1. Java 继续提供现有 ngram、标签和业务权限相关的检索能力；
2. `knowhub-agent` 负责文档解析、切片、Embedding 和向量库写入；
3. `knowhub-agent` 统一编排关键词结果、向量结果、去重、融合、重排和引用；
4. 后续如评测证明需要真正的 BM25，再评估 OpenSearch/Elasticsearch 等统一检索引擎，不在 Java 和 Python 中各维护一套重复全文索引。

### 7.4 定时任务与长任务

Java 的 `sys_job` 负责可配置的业务触发、启停、立即执行和执行日志；适合审核对账、审计报表和 AI 日报触发。Embedding、批量索引、模型生成、CI/CD 同步和长时间 Agent Run 不应占用 Java 的轻量调度线程，而应提交到 `knowhub-agent` 的 Worker，并通过任务 ID 返回状态。

### 7.5 文件、日志与敏感信息

所有二进制内容优先复用现有文件对象和存储后端。模型 API Key 不进入普通日志、Prompt、日报正文、Run 详情或错误堆栈；用户私人模型 Key 采用强加密和不可读引用，系统管理员也不能查看原文。

## 8. 第三阶段智能能力规划

第三阶段围绕独立的 `knowhub-agent` Python 服务建设智能能力。Java 后端继续负责用户身份、业务数据和权限边界，`knowhub-agent` 负责 Agent 运行、模型调用、检索编排、记忆处理和长任务执行。第三阶段的功能不是简单增加一个聊天页面，而是把知识库、学习记录、模型能力和用户画像组织成可持续运行的智能产品。

### 8.1 `knowhub-agent` 共用底座

所有 Agent 共用以下底座：

- Agent 定义和不可变版本；
- Model Gateway、系统模型 Key、用户私人 Key 和动态凭据注入；
- 会话、消息、短期上下文、历史压缩和流式输出；
- 工具注册、Schema、权限、超时、步数限制和人工确认；
- Run 审计、错误、用量、检索追踪和质量反馈；
- 短期记忆与长期记忆的存储、召回、注入、更新和删除。

#### 模型供应商与 Key

模型底座需要把“模型目录”和“凭据”分开。模型目录描述供应商、模型名、能力类型、上下文窗口、Embedding/重排能力、默认参数和健康状态；凭据只保存加密后的密文、不可读引用、所属主体、可用模型范围、状态、更新时间和轮换信息。

- 系统管理员配置系统级模型供应商和模型策略，但不能在业务日志或 Agent Run 中看到 Key 原文；
- 用户可以登记自己的私人模型 Key，系统只在调用前按授权策略解密并注入，调用结束立即释放；
- 管理员、前端接口、错误日志、Prompt 快照和 Python 普通业务代码都不能读取私人 Key 原文；
- Key 选择需要考虑 Agent、用户、组织、模型能力、降级策略和调用限制；
- 本阶段只做用量限制、失败统计和审计，不做计费和支付。

#### Agent 定义与运行

Agent 定义包括系统提示词、模型策略、可用知识库、Skill、工具白名单、记忆策略、输出格式和权限范围。正式运行使用不可变版本，编辑 Agent 会产生新版本，历史 Run 必须保留当时使用的版本、模型引用和配置快照，不能因为后续修改而无法复盘。

一次 Agent Run 至少需要关联用户、Agent、Agent 版本、会话、请求追踪 ID、模型引用、检索记录、工具调用、状态、耗时、Token、错误和最终结果。长任务必须支持排队、取消、超时、失败重试和服务重启后的状态恢复。

### 8.2 两层记忆

短期记忆是当前会话上下文，包括用户消息、Agent 消息、工具调用、工具结果和必要的压缩摘要。它服务于当前会话，不等同于用户画像。

长期记忆是用户画像和稳定偏好，不以“所有历史消息原样保存”的方式实现。长期记忆必须以 `userId + agentId` 隔离：用户在知枢 RAG-Agent 中的长期记忆不能被面试 Agent 直接读取。

新会话的上下文组装顺序为：加载 Agent 版本 → 读取当前 Agent 的长期画像 → 读取短期会话上下文 → 按需检索知识 → 组装系统提示词和本轮消息 → 调用模型。长期记忆的写入应经过提取、去重、置信度判断和用户/系统删除策略，不能把模型所有输出无条件写入画像。

记忆存储流程需要区分“原始事件”和“画像条目”：

1. 会话结束或达到摘要条件时，保存短期消息和工具事件；
2. Python 从本轮对话、训练结果、用户主动修改和业务事件中提取候选长期记忆；
3. 对候选记忆做敏感信息过滤、重复合并、置信度评估和来源记录；
4. 以 `userId + agentId + memoryType` 写入对应隔离空间，可同时保存结构化字段和可语义召回的向量；
5. 新会话只召回与当前 Agent、当前任务和权限范围相关的条目，并作为独立的长期记忆块注入系统提示词；
6. 用户删除画像、注销账号或删除 Agent 时执行级联删除、向量删除、缓存清理和审计记录。

短期消息可以存储在会话消息表或短期上下文存储中；长期画像使用独立的记忆条目存储，不能把两个 Agent 的画像混在一张没有命名空间的向量集合里。

### 8.3 知枢 RAG-Agent

知枢 RAG-Agent 面向知识库问答和知识工作。它读取用户有权访问的博客、文章、章节、项目、资源、文件和后续 CI/CD 数据，执行混合检索并返回带来源的回答。

它与普通搜索的边界是：普通搜索返回内容列表，RAG-Agent 负责多轮追问、查询改写、来源引用、无答案策略和受控工具调用。它与长期记忆的边界是：知识库是外部/组织知识，长期记忆是当前用户在该 Agent 下的画像，两者需要分别召回并在上下文中区分来源。

#### 知识库索引流程

知识库数据源可以来自上传文件、文本、URL、博客、文章、章节、项目文档、资源和后续 CI/CD 数据。索引流程为：

1. Java 保存原始数据或文件，并确认用户有权将其加入指定知识库；
2. Java 创建索引任务，传递数据源 ID、版本、内容地址和 ACL 摘要；
3. `knowhub-agent` Worker 读取授权内容，解析 Markdown、PDF、DOCX、HTML、代码或日志；
4. 按标题层级、段落、代码块和长度进行清洗、切片，记录来源位置和版本；
5. 调用 Embedding 模型写入向量库，同时保存知识库、数据源、版本、片段 ID、ACL 和索引模型；
6. 内容修改、权限变化或删除时，通过版本化重建、增量更新和删除任务清理旧片段。

#### 在线混合召回流程

用户提问后，Python 先结合当前会话和长期记忆理解问题，再执行多路检索：

- Java 现有 ngram、标签和业务搜索通道，保留当前项目的内容过滤和权限语义；
- Python 向量库通道，负责语义相似片段召回；
- 必要时追加查询改写、时间/项目/内容类型过滤和重排；
- 对结果按来源、版本和片段去重，执行 ACL 过滤，最后将有限数量的证据拼入上下文。

回答需要返回引用的内容类型、对象 ID、标题、章节/段落位置和可跳转信息。检索不到有效证据时必须明确说明无法确认，不能用模型常识伪装成项目知识。知识库中的 Prompt 注入只能作为普通内容处理，不能覆盖系统规则、工具权限和用户身份边界。

### 8.4 面试 Agent、题库与复习测试

面试 Agent 保持项目设计中的三档难度：

- 简单档：基础概念、原理、用法和对比；
- 中间档：结合简历和项目经历追问业务设计、技术选型和权衡；
- 困难档：项目扩展、故障和场景化问题，并要求把基础知识迁移到实际场景。

面试 Agent 不应把题目硬编码成一组无法演进的固定题目。题库应建设为“题目素材库 + 知识点 + 难度 + 题型 + 出题规则 + 评分规则”的可维护数据和内容集合，模型在素材和规则约束下生成具体问法。

面试 Agent 包含两种不同流程：

- **模拟面试**：Agent 根据简历、岗位、选择的难度和面试目标主动推进，覆盖提问、作答、追问、评价和训练报告；
- **学习复习测试**：用户选择知识范围，或直接使用当天学习记录作为范围，系统根据题库素材和历史答题情况生成复习测试，重点复测遗忘和反复出错的知识点。

模拟面试记录、学习记录、复习测试结果和用户主动填写的真实面试回录，都可以作为面试 Agent 的长期画像来源，但画像仍然只写入面试 Agent 的隔离命名空间。

#### 题库和素材管理

题库不是一张“固定题目随机抽取表”就结束，而是由以下内容组成：

- 题目素材：问题原型、参考答案、解析、反例、追问方向和来源；
- 知识点：技术领域、主题、标签、前置知识和参考资料；
- 题型：概念题、原理题、代码题、项目题、设计题、场景题和行为题；
- 难度：简单、中间、困难，以及可选的知识深度和场景复杂度；
- 规则：不同面试模式的出题范围、抽题数量、追问条件和重复限制；
- 评分规则：正确性、完整性、表达、证据、边界意识和改进建议。

管理员或题库维护者可以对素材进行新增、编辑、审核、停用、分类和版本管理。模型可以基于这些素材生成自然语言问法，但不能在超出岗位、知识范围和安全规则时任意扩展。

#### 模拟面试流程

用户可以选择简历、岗位描述、面试类型、难度和预计时长开始会话。Agent 根据当前画像选择开场问题，用户作答后进行必要追问；每轮记录问题、题目来源、用户回答、追问原因和阶段性评价。会话结束后生成总评、能力维度、证据、薄弱点、典型错误和下一步训练建议。

模拟面试过程中可以允许用户暂停、继续和结束，但结束后的评分和画像更新需要具备幂等性，不能因重复提交产生多份互相矛盾的训练结果。

#### 学习记录与复习测试流程

用户学习博客、文章、章节或外部知识后，系统记录学习对象、学习时间、完成状态、停留/阅读事件和用户主动标记的难点。用户可以：

- 手动指定复习范围，例如 MySQL 索引、Spring AOP 或某个项目模块；
- 直接选择“今天学习过的内容”，由系统根据当天学习历史生成复习范围；
- 指定测试题数、难度、题型和是否允许提示；
- 完成测试后查看每题解析、错题、重复错误和建议复习内容。

复习测试和模拟面试共用会话、题库、评分和面试长期画像，但不能混淆产品目的：模拟面试模拟真实面试流程，复习测试验证近期学习效果。当天学习记录应先经过权限过滤和内容快照处理，删除或无权访问的内容不能继续作为复习材料。

### 8.5 Skill 与自定义 Agent

Skill 是 Agent 可挂载的能力单元，包含说明、输入输出约束、工具白名单、资源依赖、版本和权限。Skill 资源管理可以复用 Java 的文件、资源、审核和分类能力，但 Skill 的会话挂载和安全校验由 `knowhub-agent` 执行。

自定义 Agent 复用 Agent Runtime、Model Gateway、记忆、工具和检索能力，支持创建、测试、版本、发布、分享和回滚。自定义 Agent 不允许默认获得所有知识库、工具或用户数据，发布前必须经过权限、工具和 Prompt 安全检查。

Skill 的生命周期包括上传/创建、解析、审核、版本、启用、挂载、停用和删除。挂载前需要检查 Skill 来源、版本、声明的工具、资源访问范围、Prompt 大小、依赖和是否包含危险指令；会话结束后释放临时挂载状态。普通 Skill 资源不能直接执行任意 Python、Java 或 Shell 代码，真正需要执行的能力必须注册为受控 Tool，并经过工具权限和人工确认。

自定义 Agent 创建向导至少需要配置名称、头像/描述、系统提示词、模型策略、知识库、长期记忆开关、Skill、工具、输出格式和可见范围。草稿只能由创建者测试；发布版本需要检查不可用模型、无效知识库、危险工具、循环工作流和越权范围；已发布版本不能原地覆盖，更新应创建新版本并支持回滚到已验证版本。

### 8.6 AI 日报

AI 日报是系统主动生成、用户浏览的内容产品，不是用户主动发起的对话 Agent。当前状态为第三阶段规划，现有代码尚未实现日报表、日报计划和日报页面。

#### 8.6.1 后台配置模型

后台不再采用“一个全局开关 + 一个时间 + 一个提示词”的单日报设计，而是维护多条“日报生成计划”。每条计划至少包含：

- 是否启用；
- 日报名称；
- 日报主题，例如技术动态、实验室工作、项目进展、学习复盘或资源摘要；
- 生成时间或 cron；
- 主题提示词和生成规则；
- 数据来源范围；
- 目标用户或通知范围；
- 使用的模型策略；
- 失败重试和保留策略。

配置组显式保存“每日生成份数”字段，同时维护与之对应的生成时间槽和主题条目；保存时校验有效时间槽数量与每日生成份数一致，并校验重复时间、无效主题和系统上限。未来如果一个主题需要一天生成多次，可以在同一主题计划中增加多个时间槽，不再复制一套日报模块。

#### 8.6.2 生成链路

1. Java 通过现有 `sys_job` 动态定时任务触发对应日报计划；
2. Java 根据计划 ID、业务日期、时间槽和数据范围创建幂等的生成任务，并调用 `knowhub-agent`；
3. `knowhub-agent` 聚合授权范围内的 KnowHub 内容，按主题提示词生成 Markdown 日报；
4. Java 保存日报记录、标题、正文、摘要、计划快照、生成时间、状态、失败原因和关联 Run ID；
5. 生成成功后按计划决定是否写入现有通知中心，通知只负责提醒，日报正文仍由日报模块展示；
6. 失败任务支持重试、人工立即执行和错误日志追踪，不影响其他计划或下一日生成。

日报任务的幂等键至少包含“计划 ID + 业务日期 + 时间槽”。同一时间重复触发不能生成重复日报。模型 Key、完整 Prompt 和用户私人凭据不能写入日报内容或普通日志，只保存脱敏的版本和引用。

#### 8.6.3 数据来源与内容边界

第一版优先使用 KnowHub 内部数据：当天发布或更新的博客、文章、章节、项目、资源、审核动作、学习记录和 Agent 运行摘要。外部新闻、RSS 和第三方 API 可以作为后续数据源，不应在第一版把外部抓取和日报核心流程耦合死。

AI 日报默认是 AI 生成的只读内容。管理员可以停用计划、删除整期、重试或重新生成，但默认不提供逐字编辑正文的后台能力；如果未来需要人工校对，应单独增加“审核/发布”状态，不把内容编辑混入普通配置页。

#### 8.6.4 前台功能

- 首页展示最近一期或按用户范围可见的日报卡片；
- 日报列表按时间、主题和计划筛选并分页；
- 日报详情使用现有 Markdown 渲染链路；
- 支持按日期、主题和关键词检索历史日报；
- 支持查看生成状态、来源摘要和重新生成结果，但不向普通用户暴露 Key、内部 Prompt 和无权数据。

#### 8.6.5 与其他能力的关系

- 与 `sys_job` 的关系：日报使用现有动态调度，不新建平行调度中心；
- 与通知的关系：通知只负责提醒和跳转，不保存日报正文；
- 与知枢 RAG-Agent 的关系：日报是系统定时生成的内容，RAG-Agent 是用户主动问答；日报可以作为 RAG 的一个受控数据源；
- 与面试 Agent 的关系：日报可以汇总学习复盘结果，但不直接读取面试 Agent 的私有长期画像；
- 与模型底座的关系：日报复用 Model Gateway 和凭据策略，不单独保存或配置一套 API Key。

### 8.7 Agent 运行保障与质量闭环

Agent 上线后需要持续回答“是否可用、为什么失败、是否越权、如何改进”这几类问题。运行保障包括：

- 为每次 Agent Run 保存 Agent 版本、模型引用、会话、请求追踪 ID、检索结果、引用来源、工具调用、状态、耗时、Token、错误和最终结果；
- 支持排队、取消、超时、失败重试和服务重启后的状态恢复，长时间索引和生成任务不能依赖浏览器一直保持连接；
- 统计成功率、首 token 延迟、总耗时、检索命中率、引用采纳率、工具失败率、用户反馈和重复问题，按 Agent、模型和版本查看；
- 对回答进行点赞、点踩、纠错、引用质量评价和问题标记，反馈需要能定位到模型、Prompt、检索、权限过滤或前端展示环节；
- 对 Prompt 注入、越权读取、危险工具调用、敏感数据泄露和异常调用频率建立检测与审计；
- 本阶段只做调用次数、Token、耗时、失败和限额管理，不建设计费、套餐和支付体系。

## 9. 后续发展规划

以下内容不属于第三阶段的 Agent 建设任务，而是 KnowHub 在现有知识库、项目和系统底座稳定后继续发展的产品方向。它们分别解决网站业务扩展、项目协作、代码仓库展示和内容发现问题。

### 9.1 协作开发模块

协作开发模块面向实验室或组织内部的项目协作，产品形态参考 ClickUp 一类的项目协作空间。它不是 CI/CD 检索的附属页面，也不是简单的项目状态字段，而是在现有项目展示模块之上增加可执行的任务协作能力。

主要能力包括：

- 在项目下创建 Story、需求、任务、子任务和缺陷，记录标题、描述、优先级、负责人、参与人、标签、截止时间和当前状态；
- 将任务组织到待办、进行中、评审、已完成等工作流中，支持列表、看板、时间线和日历等视图；
- 按版本、迭代或阶段划分里程碑，记录里程碑目标、开始/结束时间、关联任务、完成进度和延期原因；
- 支持任务之间的前置依赖、阻塞关系、关联文档、关联项目版本和关联代码提交，为后续 Git 平台集成预留引用关系；
- 提供项目成员协作、评论、附件、动态记录、任务变更历史和通知，成员只能访问自己所属项目及其授权范围内的任务；
- 支持项目负责人配置工作流、任务字段、标签和成员权限，并通过项目概览查看任务分布、里程碑进度、逾期任务和成员负载；
- 与现有项目模块联动：项目模块负责成果展示、项目资料和归档，协作模块负责过程中的 Story、任务、里程碑和进度记录，两者共享项目、成员和权限关系。

该模块的目标是让 KnowHub 从“项目成果展示与归档”进一步具备“项目过程协作与进度管理”能力，但不在此模块内直接实现代码托管、构建执行或自动部署。

### 9.2 Git 平台集成与代码仓库展示

Git 平台扩展用于把项目与代码仓库连接起来，使 KnowHub 能够提供类似 GitHub 的仓库浏览和版本记录体验。它与 CI/CD 流程化检索分别建设：CI/CD 关注构建、部署和日志问答；Git 平台扩展关注仓库内容、代码版本和开发历史展示。

后续可以逐步提供：

- 关联外部 Git 平台或接入内部 Git 服务，维护仓库、项目、仓库地址、默认分支和访问凭据引用；
- 展示仓库目录、文件内容、分支、标签、提交记录、提交详情、版本差异和发布版本；
- 支持按提交、作者、时间、分支和标签查看代码历史，提供代码文件在线浏览和版本切换；
- 将仓库、分支、提交、版本和变更文件关联到 KnowHub 项目、Story、任务、里程碑和项目文档；
- 在项目详情中展示代码仓库入口、当前版本、最近提交、版本说明和项目成员信息；
- 对仓库同步状态、访问权限、凭据失效、分支变化和历史版本同步失败提供后台管理和错误记录。

该方向初期以“展示和同步”为主，不要求 KnowHub 自建完整 Git 托管服务；是否直接托管仓库、是否支持在线编辑、是否增加 Issue/Merge Request 等能力，留待 Git 平台基础链路稳定后再确定。仓库代码、提交内容和凭据必须遵循项目成员权限，不能因为项目公开展示就默认暴露所有分支和历史版本。

### 9.3 插件市场与网站业务扩展

插件的目的，是让 KnowHub 可以在不频繁修改核心业务代码的情况下，持续拓展网站的功能和业务类型。未来出现新的内容形态、审核方式、通知渠道、导出格式、检索策略或外部系统连接时，可以通过插件增加能力，而不是每次都把功能硬编码进主工程并重新改造核心模块。

插件不是 `knowhub-agent` 的 Skill，也不是允许用户上传并执行任意脚本的机制。插件是由平台管理员安装和治理的 Java 业务扩展，面向网站宿主提供稳定扩展点；Skill 面向 Agent 的能力挂载，二者的运行环境、生命周期和安全边界不同。

#### 技术栈与运行方式

- 使用 **PF4J** 作为 Java 插件化框架，利用独立 ClassLoader 支持插件的加载、启用、停用和卸载；
- 新增 `knowhub-spi` 模块，只放宿主公开的扩展点接口和稳定的数据契约，插件不能直接依赖 KnowHub 宿主内部业务实现类；
- 宿主使用 `JarPluginManager` 扫描 `plugins/` 目录并管理插件生命周期，插件以带 manifest 的 JAR 包交付；
- manifest 至少声明插件 ID、名称、版本、所需宿主 API 版本、扩展点类别、依赖插件和能力权限；
- 插件包本体复用 RustFS 和现有文件存储底座，数据库保存插件元数据、版本、对象 Key、状态和安装记录；
- 插件管理复用现有用户、角色、菜单、按钮权限、操作日志和审计机制，安装、启用、停用、升级、回滚和卸载均需留痕。

#### 插件扩展类别

首批扩展点可以按网站业务能力划分为：

- **内容渲染扩展**：增加 Markdown 渲染规则、代码高亮主题、自定义容器和指令渲染；
- **内容审核扩展**：接入敏感词、图片识别、AI 预审、自定义审核动作和审核结果回调；
- **存储扩展**：接入外部网盘、二次转码、自定义上传处理和下载鉴权；
- **导出与格式转换扩展**：支持 PDF、EPUB、DOCX 等导出，以及 Markdown 与其他格式互转；
- **通知扩展**：接入邮件、企业微信、钉钉、Webhook 等通知通道和模板；
- **统计与看板扩展**：增加自定义统计指标、报表和可视化图表；
- **搜索与检索扩展**：接入其他搜索引擎，或为特定业务对象提供专用检索策略；
- **AI 扩展**：扩展知识问答策略、RAG 切片器或受控 Agent 工具，但必须遵守既有模型、权限和审计边界；
- **定时任务扩展**：注册插件自己的清理、同步和巡检任务，并复用定时任务白名单与执行日志。

#### 插件市场功能

插件市场需要支持插件发布、元数据维护、版本归档、兼容性检查、签名校验、下载、安装、启用、停用、卸载、升级、回滚、依赖检查和冲突检查。管理端需要展示插件状态、作者、版本、宿主 API 版本、扩展类别、权限声明和运行错误；插件配置应由插件声明配置项，宿主提供统一的配置管理入口。

插件运行必须具备签名校验、能力声明、权限校验、异常隔离和 ClassLoader 卸载清理。插件可以扩展网站功能，但不能绕过 Java 业务 Service 的权限检查，不能默认读取所有数据库、文件、用户私有数据或模型凭据。插件市场的目标是让网站具备持续扩展能力，不是建立一个无约束的远程代码执行入口。

### 9.4 高级推荐与学习路线可视化

在现有标签、浏览、点赞、收藏、评分和内容关系基础上，后续可以继续增强内容发现能力：

- 引入更丰富的内容相似度、用户兴趣和学习进度特征，改进博客、文章、项目和资源的个性化推荐；
- 根据知识点、标签、章节先后关系和项目实践建立学习路径推荐；
- 提供更直观的学习路线图、知识结构图和阶段完成度展示，帮助用户理解“先学什么、正在学什么、下一步学什么”；
- 推荐结果保留触发原因和来源，不因引入算法而绕过内容可见性、项目成员权限和资源访问限制。

这部分属于现有内容平台之上的产品增强，不能替代第三阶段的知枢 RAG-Agent。推荐解决内容发现和学习路径组织，RAG-Agent 解决基于用户问题的知识召回与回答。
